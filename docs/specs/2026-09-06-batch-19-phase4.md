## 1. Goal

After this batch, an adopter installs `houserules` from a real
channel — no local clone, no cargo toolchain — and every consumer
this repository ships points at that channel: the README's
install blocks (HR-064 retires the build-from-source section),
the seeded CI workflow (HR-063 gains its install step), and the
release flow keeps the README pins current (HR-049). External
registry acts (the mise registry PR, an asdf plugin repository, a
tap, Scoop/winget) stay owner-attended per the decision 3
precedent; this batch makes them possible and documents each act.

## 2. Decision: the release pipeline (library research at spec
time, per quality.well-maintained-libraries; the owner rules)

The channel bedrock is GitHub Releases carrying per-target
binaries (linux x64/arm64, macOS x64/arm64, Windows x64) with
checksums, triggered by the existing release-please tag (plain
`v<version>` per §5.20; the include-component-in-tag flip rides
this batch as the first config-touching task).

Candidates researched 2026-09-06:

- **cargo-dist 0.32.0** — last release 2026-05-22, actively
  maintained through 2026 (0.29 absorbed Astral's fork features
  back upstream; 0.32 removed its npm installer's external deps).
  Generates the whole release workflow: matrix builds for the
  five targets, archives with ubi-compatible target-triple
  names, sha256 checksums, a shell + powershell installer, an
  optional Homebrew formula, GitHub Releases upload keyed on the
  v* tag. Trigger composes with release-please (tag-push).
  RECOMMENDED — the maintained, purpose-built tool; custom
  workflow code shrinks to near zero.
  OWNER'S CHOICE (ruled 2026-09-06 at this gate): cargo-dist.
  The task pins it exactly with the full dependency vet.
- **taiki-e/upload-rust-binary-action v1.30.2** — last release
  2025-04-17 (~17 months); historically solid, momentum visibly
  reduced. Smaller surface: builds + uploads per target, but the
  installers, checksums layout, and formula would be hand-rolled
  around it — more custom code than cargo-dist.
- **Hand-rolled matrix workflow** — the custom solution the
  governance rule exists to avoid; on the table only if the
  owner prefers zero third-party release tooling.

Exact-pin posture: the chosen tool is pinned exactly (the
cargo-dist plan/config pins its version; actions pin by tag
against the vetting record). The deep vet (maintenance, releases,
ownership, the 2025 axo turbulence and its resolution) rides the
adopting task's dependency_vetting.

## 3. macOS signing decision (HR-048's named deliverable)

Options for the owner at this gate: (a) UNSIGNED with the
documented `xattr -d com.apple.quarantine` note in the install
docs — zero cost, the common OSS posture, revisitable;
(b) ad-hoc signing in CI (`codesign -s -`) — removes some Gatekeeper
friction, no identity; (c) full Developer ID signing +
notarization — needs the owner's Apple Developer account
(owner-attended secrets), real cost. RECOMMENDED: (a) now,
revisit at 1.0.

## 4. The channels this batch wires

- GitHub Releases: binaries + checksums at every release-please
  release (the pipeline of §2).
- mise via ubi: works from correctly named release assets with
  no registry act; the docs gain the `mise use ubi:jblossey/
  houserules` form. The mise-registry short-name PR is an
  owner-attended follow-up, documented.
- The curl-to-sh installer: cargo-dist's generated installer if
  §2 rules cargo-dist; otherwise deferred with a reason.
- Homebrew tap / asdf plugin / Scoop / winget: the assets and
  docs this batch ships make them possible; each act is
  owner-attended and documented in the runbook, not performed.

## 5. The consumers flip (HR-049, HR-063, HR-064)

- README: the build-from-source section retires; the install

  state-only-the-source method (control runs included). The
  pinned-tag forms wire into the release flow (release-please

## 6. What does not change

bin/houserules.mjs, the frozen corpus, make-corpus.mjs (phase 5,
per §5.35); HR-066's checker subcommand (phase 4/5 boundary —
this batch takes it ONLY if the pipeline work leaves room and
the owner gates it in); the payload's content otherwise.

## 7. Risks and bounds

The pipeline cannot be fully live-verified before a real release
exists; the batch's live proof is a WORKFLOW-LEVEL dry run
(cargo-dist plan/build locally for the host target, plus the
generated workflow validated in CI on a prerelease tag or
workflow_dispatch against a draft release — the exact mechanism
settles in the plan). The first real release remains
owner-attended (the release-please PR merge), after which HR-049
and HR-063's ends are re-verified live; the acceptance record
notes this two-step reality.
