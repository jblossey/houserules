## 1. Goal

Scope goal (discussion 59): per change, houserules says which rules apply, which are proven, which are only judged, what is unverified, and who must review. Other concerns connect through adapters.

A fix must do one of three things: cut the number of changes that need a human, cut the human cost per change, or catch escapes cheaply after merge (discussion 59).

Constraint (5.100): every function of section 6 remains at 2.0.0, unless the owner rules otherwise for that function. An issue's proposal is not such a ruling.

Done means:

- Every row of section 3 ships in exactly one batch, and that batch's spec names it (section 9).
- Every function of section 6 is kept, or the owner's ruling that changes it is in design.md.
- Every open GitHub issue closes with the 2.0.0 release: 35, 38, 41, 50, 58, and 60 to 73.
- An install at any released kit that has the Rust binary (0.3.0 and every 1.x tag) reaches 2.0.0 through `houserules update` and the upgrade guide (section 7). The pre-release 0.2.0-alpha has no Rust binary and is out of scope.
- This repository runs on the 2.0.0 kit before the release PR merges (section 8).

## 5. Interactions between rows

Each "See M" item is resolved by its ruling in section 10; the other items are design facts the batch specs carry.

1. **HR-173 inside HR-183.** Issue 63's runner contract is the general form of HR-173's "run a project command, read its exit status". Ruled: HR-173 closes as the exit-code runner of HR-183 (M14, 5.121).
2. **HR-163 after HR-183.** Each mechanize candidate becomes a runner check or a `ruled-keep` tag; the runner exists first.
3. **`archive` under HR-180.** Issue 60 removes `archive` from the core CLI, but `archive` also moves superseded and retired knowledge entries (`archive.rs` module doc). See section 6, M3.
4. **Deferrals and technical debt under HR-180.** Issue 60's adapter interface is read-only: it resolves an id and returns status and title, and `audit` checks that each commit's id resolves. Nothing in it lets houserules file an item. Today the backlog records every deferral: `process.no-tech-debt` allows a deferral only as a backlog item with a reason; `process.bounded-review-loop` turns the open findings at the re-review cap into one backlog item; Minor polish goes to `backlog/parked.json` as PP ids; a `mechanize` proposal of `stats` files a backlog item (`process.knowledge-earns-its-place`); `check-backlog` checks the records. With a read-only adapter, filing falls to the agent, houserules cannot check that a deferral was filed with its reason or that a review cap produced its item, and parked polish, amendments, and decisions have no counterpart. Beads can hold such items (section 2: `chore` type, labels, `defer --reason`, `discovered-from`). See M2 and M3.
5. **HR-178 under HR-182.** `knowledge-base.cite-durable-refs` is in the `knowledge-base` topic, which issue 62 keeps in the minimal default. D6 stands under packs.
6. **HR-162 under HR-182.** Pack files ship in emit form, so `pack add` and `update` rewrite nothing on a fresh install.
7. **Kit updates of seeded entries under HR-182.** Issue 62 makes packs seed-once ("`update` never overwrites them"). Today `update` keeps each kit-shipped entry in sync through a per-entry baseline and never replaces an entry the adopter changed (`baseline.rs`); `.houserules.json` `overrides` silences a kept change. Seed-once packs would stop kit fixes to seeded rules from reaching adopters. See M4.
8. **Built-in check types under HR-183.** Issue 63 re-implements seed checks that duplicate a tool by calling the tool (commitlint for commits). Today the six check types run inside the binary with no other tool installed, and the commit-msg hook and `check-commit` depend on the `commits` type. See M5.
9. **Area rules under HR-184.** Areas are globs (`knowledge/areas.json`; for example `Cargo.toml` and `crates/**` in one area). `.claude/rules/<area>.md` loads on a glob match through its `paths:` frontmatter. A path-scoped AGENTS.md sits in one directory, so an area whose globs are not one directory prefix has no exact AGENTS.md home. See M6.
10. **The reference workflow and the process pack.** The kit-owned templates and skills cite seeded `process.*` ids, and `check-knowledge` fails a citation of a seeded id that is not in the knowledge base (`kit_citations.rs`). A reference workflow without the process pack fails that lint. See M7, M7b, M7c. A pack depends on no other pack (5.109), and every install gets the core texts while a default install has only the `knowledge-base` pack, so the enumeration `.superpowers/sdd/2026-10-10-batch-33/cross-pack-refs.py` (output `cross-pack-refs.txt`, 2026-10-16) lists what the minimal default would fail on: six seeded `see` links that cross from one pack to another (`check-knowledge` fails a dangling `see`) and two citations of process ids in the core migrating-knowledge skill (lines 17 and 237). Batch 33 removes the six links (an entry's body may still name the id in prose, which no gate reads) and rewords the two citations; batch 34's rewrite (6.4) moves the `verify` path of `knowledge-base.controller-rules-are-tagged` off the orchestrating skill. The minimal default lands with the workflow move: in batch 33 `init` still installs the 1.4.0 seed set, as five packs, and the workflow files; batch 34 moves the workflow files to the reference-workflow package (HR-181) and makes the `knowledge-base` pack alone the default, and its live run proves HR-182's acceptance that a minimal init passes every gate. Until batch 34 merges, removing the process pack on main fails the kit-citation lint on the core workflow files; main is unreleased, so this red reaches no adopter.
11. **AGENTS.md under HR-184.** `AGENTS.md` is seed-once (`houserules files`) and holds the project's own prose. See M9.
12. **Riders under HR-181.** HR-129, HR-153, HR-165, HR-166, HR-150, and HR-144 edit files that move to the reference workflow. They apply to the moved files.
