## 3. The runner contract (HR-183, 5.107, 199(1), 200(1))

### 3.1 The project's tools

`.houserules.json` gains `runners`: `{ "<tool>": { "command": ["<program>", "<arg>", ...], "parser": "sarif" | "exit-code", "install": "<one install line>" } }`. Only the project writes it; `init`, `init --workflow`, `update`, and `pack` keep its value (the marker writer lays `.houserules.json` out again). The whole command line, its parser, and its install line come from this object (199(1), 200(1)). A program given with a path separator resolves against the install root.

### 3.2 The check

```json
{ "type": "runner", "level": "fail", "tool": "semgrep", "files": ["src/**"], "scope": "changed" }
```

- `tool` is a key of `runners`; a pack's check holds only `tool`, `files`, and `scope` (200(1)).
- Trigger: the check is triggered when a changed file matches `files` (default `**`). Untriggered: row `pass`, evidence `not triggered`, and no process starts.
- `scope: "changed"` (the default) appends the triggering files to the command, one argv entry each, with no shell, in batches of at most 200 per call. `scope: "tree"` appends nothing and makes one call; the tool reads the install root.
- The process runs with the install root as its working directory and the environment of `audit`. No timeout applies: the tool's run time is the project's choice, and a CI job's own timeout bounds a tool that hangs.
- The tree (C13): every other row reads files at `--head`, and the tool reads the working tree, so before a triggered runner check starts, `audit` confirms that the working tree is the tree at `--head`. `--head` must resolve to the checked-out commit, and no file the tool reads may differ from its content at `--head`: for `scope: "changed"` the triggering files, for `scope: "tree"` every tracked file (`git diff --quiet <head> -- <paths>`; untracked files are not tested). Otherwise `audit` prints `runner tool "<tool>" needs the tree at --head checked out: <reason>` and exits 2 with no rows; `<reason>` is `HEAD is <short sha>, --head is <short sha>` or `<path> differs from --head`. Untracked files are an accepted gap: a `scope: "tree"` tool walks the directory, so a finding in an untracked file that git does not ignore counts in the row; refusing a run while untracked files exist would block every local run with a scratch file, and a CI clone has none.
- CI (203): the `actions/checkout` step of the seeded `knowledge.yml` and of this repository's `ci.yml` (its `checks` job, which runs the audit) gains `ref: ${{ github.event.pull_request.head.sha }}`, the form the checkout's own README gives for the PR head. On a pull request every step of the job, the audit included, judges the PR head; on a push the expression is empty, so `ref` is `''` and the checkout keeps the event's ref (`ci-checkout-ref-docs.txt`). Under the ff-only merge (design.md 198) the PR head is the tree that lands (C14). Every form of the seeded workflow carries the step: the top-level and the subdirectory forms and each tracker's form. `update` delivers it through the file's baseline: an unmodified copy is rewritten (`wrote .github/workflows/knowledge.yml`), and a modified copy is kept (`kept .github/workflows/knowledge.yml (locally modified)`) and, when its text lacks `ref: ${{ github.event.pull_request.head.sha }}`, `hand_step_for_kept` adds for every tracker the hand step `<path> lacks the PR-head checkout; add ref: ${{ github.event.pull_request.head.sha }} under with: of its actions/checkout step` after the tracker's own, the no-tracker form included (D10); the upgrade guide's batch-35 section gives the same step.
- `parser: "sarif"`: each result is a finding at the level SARIF 2.1.0 3.27.10 assigns it (2): a `kind` other than `fail` gives `none`; else `result.level`; else, when `result.provenance.invocationIndex` is 0 or more, the level of the first `ruleConfigurationOverrides[]` entry of that invocation whose `descriptor` names the rule (by `index`, else `id`); else the rule's `defaultConfiguration.level`, the rule found in `tool.driver.rules` by `ruleIndex`, else by `ruleId`; else `warning`. A rule held in `tool.extensions` is not read (its results take `warning`). Levels `error` and `warning` count, `note` and `none` do not. The path is the result's first `artifactLocation.uri`, made relative to the install root with `/` separators (`file://` and `originalUriBaseIds` resolved; a path outside the root kept as given); a result with no location is a finding with `path` and `line` `null`. The exit status is ignored when stdout holds valid SARIF. No SARIF on stdout, invalid SARIF, or `invocations[].executionSuccessful: false` is a setup error. The findings of batched calls are merged in call order.
- `parser: "exit-code"`: every call exits 0: pass. Otherwise a violation whose evidence is the first stderr line of the first call (in call order) that exited non-zero, or `exited <n>` when that stderr is empty; the row carries no `findings`.
- A `sarif` row's evidence names the first finding (`<path>:<line> <ruleId>: <message>`, or `<ruleId>: <message>` with no location) and the rest as `and <n> more`; the row gains `findings`, each `{ "path", "line", "rule", "message" }`, which lists only the results that count (`error`, `warning`), in call order. A result with no `ruleId` takes the `id` of the rule its `ruleIndex` names, else the designed token `(no rule id)`. A `sarif` row with no finding passes with evidence `no findings in <n> calls`, an `exit-code` row with evidence `exited 0 in <n> calls`, each `1 call` for one call; an untriggered row keeps `not triggered`. A `sarif` row that ran carries `findings` (`[]` when it passes); an untriggered row carries none. An empty or blank `ruleId` counts as absent (the indexed rule, then `(no rule id)`), and an empty or blank `message.text` gives `(no message)`, so no evidence holds an empty slot. A finding with a path and no line reads `<path> <rule>: <message>`; the rest of the findings read `and <n> more` after one space. A `level` outside SARIF's four values is invalid SARIF. A location's `uri` is resolved with its `uriBaseId` from `originalUriBaseIds` as RFC 3986 reference resolution and percent-decoding give it (dot segments removed); a resolved path under the install root is made root-relative, one outside it keeps its fully resolved form (base applied, for example `file:///elsewhere/src/x.rs`), and a `uriBaseId` the run does not define leaves the `uri` relative to the install root; a `file://` URI with a host other than `localhost` is kept as given. Because the resolution is the library's: a query or fragment is dropped from a path (`src/a.rs#L3` reads `src/a.rs`); a base that is not a `file:` URI gives the fully resolved URI; a bare `C:/src/a.rs` parses as a URI with scheme `c` and is kept as given; a backslash in a relative reference is a separator; a relative base resolves against its own `uriBaseId`, else the install root, to a depth of 8. The `exit-code` evidence is the first non-blank stderr line, trimmed; a run stops at the first call that exits non-zero, and a process ended by a signal gives the evidence `ended by a signal`.

### 3.3 Setup errors

- `check-knowledge`: `knowledge/<topic>.json <id>: runner tool "<tool>" is not defined in .houserules.json runners`; for an entry of a pack copy the file is `knowledge/packs/<pack>.json`, as the existing pack and override lines name it. A `runner` check with no `tool` gets `<file> <id>: check "runner" needs "tool"` from every source, local, pack copy, or override; `check-knowledge` checks the required fields of every type this way, on the effective check of every active entry (Task 2 review, issue 1: an override `grep-absent` with no `files` passed before).
- `check-knowledge`, for the `runners` object itself: `.houserules.json: runners must be an object`; for each entry: `.houserules.json: runners.<tool> must be an object` (an entry that is no object), `.houserules.json: runners.<tool>.command must be a non-empty array of strings`, `.houserules.json: runners.<tool>.parser must be "sarif" or "exit-code"`, `.houserules.json: runners.<tool>.install must be a non-empty string`, and `.houserules.json: runners.<tool> has an unknown key "<key>"`. Each line names the first fault of its entry; the entries are checked in key order.
- `audit`, for a check and a program: `<id>: check "runner" needs "tool"` (a runner check with no `tool`), and `runner tool "<tool>" (<program>) could not start: <the OS error>` (a program found but not startable). The tree test runs before the program is started, so the tree line comes first when both faults hold.
- `audit`, for a SARIF run: `runner tool "<tool>" printed no SARIF on stdout`, `runner tool "<tool>" printed invalid SARIF: <first line of the parse error>`, and `runner tool "<tool>" reported executionSuccessful: false`.
- `audit`, for a triggered check only: an undefined tool prints `runner tool "<tool>" is not defined in .houserules.json runners`; a malformed entry prints its `check-knowledge` line; a defined tool whose program is not found prints `runner tool "<tool>" (<program>) is not installed: <install>`; the tree test of 3.2 prints its line; a SARIF setup error prints its line. Each exits 2 with no rows.
- The seeded CI workflow installs no project tool; a project that uses runners adds their install steps to its own CI, and the line says what to run.
- No network by default: the migrating-knowledge skill's runner section teaches local rule files (no registry config), the tool's metrics and every other call home switch off (Semgrep: `--metrics off` and `--disable-version-check` in the command; the version check is a separate server contact, `semgrep-network-docs.txt`, found by the live run), and an exact tool version.

### 3.4 The port and the built-in runners

Inside the binary a check type is a runner: the six built-in types and `runner` each produce rows through one interface. The six built-ins keep their names, fields, and rows and need no tool (5.107); `check-commit` and the commit-msg hook keep their output through the built-in `commits` runner.

### 3.5 SARIF types

The batch owns minimal `serde` deserialize types for the fields 3.2 reads (199(5)), and resolves and decodes a location's URI with the `url` crate (`Url::join`, `percent_encoding::percent_decode_str`), at the version `Cargo.lock` already holds through `axoupdater` (2.5.8), added as a direct dependency with `cargo add url@=2.5.8 percent-encoding@=2.3.2` (`url` does not re-export `percent_encoding`; both versions are already locked), so no new crate enters the lock file (decided under design.md 204 as D7 on the Task 3 review, issue 2; `url-crate-vetting.txt`: servo/rust-url, 2.5.8 of 2026-01-05, about 978 million downloads). The SARIF types: per run, `tool.driver.rules[]` (`id`, `defaultConfiguration.level`), `invocations[]` (`executionSuccessful`, `ruleConfigurationOverrides[]` with `descriptor.id`, `descriptor.index`, and `configuration.level`), `originalUriBaseIds`, and `results[]` (`ruleId`, `ruleIndex`, `kind`, `level`, `provenance.invocationIndex`, `message.text`, `locations[].physicalLocation.artifactLocation` with `uri` and `uriBaseId`, and `region.startLine`). Unknown fields are ignored. The reasons: the established crate is stale and no maintained crate reads SARIF (2). Best case of serde-sarif: 2.9 million downloads and a full typed model of the standard, writing included. Reversal condition: a maintained, well-adopted crate that reads SARIF appears, or the kit needs to write SARIF.

### 3.6 Testing

The suite runs a committed fake tool, `tests/fixtures/runner/fake-sarif.sh`, through `sh` on every system: it prints fixed SARIF, exits with a fixed status, and writes a marker file when run. `exit-code` cases use `sh -c 'exit 3'`. The live run uses a real Semgrep at an exact version with `--metrics off` and a local rule file.

## 4. Overrides and promotion candidates (HR-188)

- A judged row of a review deliverable (`rule_adherence[]` of a task review, re-review, or branch review) may carry `override`: `{ "result": "pass" | "fail", "by": "<person or role>", "reason": "<text>" }`, written by the person who runs the work when they or the owner rule against the reviewer's verdict; the orchestrating skill says so.
- Per judged rule, `stats` gains `verdicts` (judged rows with a `pass` or `fail` result), `overrides`, `override_rate` (overrides over verdicts; `null` at zero verdicts), and `cost`: for each review that judged the rule (once per review, whatever number of its rows judge the rule), the review file's bytes divided by its judged rows, rounded down, summed, in bytes; `null` for a rule with no judged rows. The `stats --help` text calls it the sum of each judging review's share of its bytes.
- `stats --window <N>` reads the `N` most recent of the named workspaces (the help names the value `N`); a window of one workspace drops the workspace prefix of task labels, as a single named workspace does today: by the `YYYY-MM-DD` prefix of the folder name, then by name; a folder with no date prefix sorts before every dated one. `n` above the count reads all; `n` of 0 is refused with `--window must be 1 or more` and exit 2 (decided under design.md 204, plan review question Q1). With no flag `stats` reads all, as today.
- `mechanize` fires as today and in addition only when `override_rate` is at most 0.2 or `null` (an assumed threshold for issue 68's "low override rate", C2); its evidence gains `override_rate` and `samples`: up to three entries of the `issues[]` of task reviews and the branch review whose `rule` is the id (not a re-review's `new_breakage` or a spec review's `findings`), the most recent workspace first, and within one workspace in file order. For every proposal (`retire`, `demote`, `mechanize`, the budget's catch rate) a sanctioned fail counts as a fail did before this batch: it fires the rule; only `violations` and the rule's `fails` leave it out (spec 6). ## 6. `self_audit` and sanctions (HR-138, HR-152)

- Comparison (C3): the `report-field` check whose field is `self_audit` (the kit's `process.deliverables-json`) compares, in a `--report` audit, the report's `self_audit.summary` and deterministic rows with the audit's final output for the same range, both parsed: the comparison runs in `cmd_audit` after the sanctioned annotation, the `empty range:` prefix, the summary, and the reference verdict (`summary.reference_fail`) exist, and then sets the comparing row's result and the summary counts it moves. It compares only when the report's `summary.base` and `summary.head` name the audit's commits: each recorded sha is resolved with `git rev-parse --verify <sha>^{commit}` and compared as a full sha, so a short sha that a repack lengthened still matches; a sha that does not resolve gives the not-compared evidence; otherwise the row's evidence adds `self_audit covers <base>..<head>; this run covers <base>..<head>: not compared`. The compared set leaves out the comparing row and the summary counts it moves (its own result in `pass`, `fail`, `warn`, or `skipped`, and a booked fail of it in `sanctioned_fail`); every other count is compared, and a booking on the comparing rule is judged on the row's final result (Task 5 review, issues 2 and 3, and its fix round). A difference fails the row: `self_audit differs at <JSON path>`. A draft (`self_audit: null`) passes as today. An install without the process pack has no such check.
- `--workspace` mode: `non_empty` applies to each report the check triggers, and the first report whose value is empty fails the row with `<report>: report field <f> is empty`; `covers_ids` does not run there (each report has its own `--ids`; C12): a passing row of an entry that holds it carries the count line of spec 5 with `; covers_ids needs --report` appended, for example `report field knowledge_used is set in 6 of 6 reports; covers_ids needs --report`, so HR-176's count stays on every row (decided under design.md 204, D11; Task 5 review, issue 1).
- C12: a `--workspace` run does not compare. Best case of comparing there: every report checked at the branch review. Reason: a self_audit records its range but not its `--ids`, so the package cannot be rebuilt. Reversal condition: `self_audit` records its `--ids`.
- The implementer template: after the last edit to the report, run the audit again and re-copy `self_audit`; a comparison fail means the copy is stale.
- Sanctions: `--sanctioned <rule>=<ref>` accepts a judged rule of the package; every sanctioned row, deterministic or judged, gains `"sanctioned": "<ref>"`, and a booking on a judged row is never stale. A deterministic row keeps its evidence suffix and exit (batch-34 C45). The task-reviewer and branch-reviewer templates keep `sanctioned` on a row they judge.
- `stats`: a `fail` row with `sanctioned`, or a deterministic `fail` row whose evidence ends with `(sanctioned: <ref>)` (the form since batch 32), counts under the rule's `sanctioned` and in a top-level `sanctioned` list (`id`, `workspace`, `task`, `ref`; a row of a branch review or a spec review names its file as `task`), never in `violations` or the rule's `fails` (HR-152; in 2.0.0 by design.md 192 and 193).

## 7. Workspaces out of git (HR-213, design.md 195, 199(4))

- Home: `.houserules/work/<YYYY-MM-DD>-batch-<n>/`. A project sets another location with the top-level key `workspaces` of `.houserules.json` (a path relative to the install root); `init`, `init --workflow`, and `update` keep its value. This repository sets `".superpowers/sdd"`. A value that is not a non-empty string, is absolute, or holds a `..` segment is named by `check-knowledge`: `.houserules.json: workspaces must be a relative path inside the install root`.
- Ignore: `init` writes `.houserules/` to `.gitignore` in place of `.houserules/step/`; `update` replaces a `.houserules/step/` line with `.houserules/`, and adds `.houserules/` where neither line is present. The lines: `merged .gitignore (.houserules/step/ replaced by .houserules/)`, `merged .gitignore (.houserules/ added)`, `kept .gitignore (.houserules/ already present)`, and `wrote .gitignore` for a new file; `init` prints the `kept` line, and `update` prints no line for a file that already holds `.houserules/` (D10). A line reads as git reads it: unescaped trailing spaces do not count, leading spaces do. The default location `.houserules/work`, when the `workspaces` key is not set, the folder exists, and git does not ignore it, is named by `check-knowledge` (an absent folder holds nothing git could track, so a fresh clone and an install that never made a workspace get no line; plan review round 2, P3): `.houserules.json: workspaces path ".houserules/work" is not ignored by git; add .houserules/ to .gitignore`, so an install whose `.gitignore` lost `.houserules/` is named. A location the project sets with `workspaces` is the project's choice: tracked or ignored, it gets no line (decided under design.md 204, question R4-Q2). The test asks git about the path with a trailing `/` (`git check-ignore -q <p>/`), because the usual ignore line `<p>/` matches only a directory and git cannot tell that an absent path is one: the verdict is the same whether or not the folder exists, as in a fresh CI clone (`spec-review-r2-probe-check-ignore.txt`).
- Readers: the reference workflow's skills name the workspace as "the `workspaces` location (default `.houserules/work/`)", and the orchestrating skill names the ledger `progress.md` in each workspace; core texts use the same neutral wording.
- `verify` paths: `check-knowledge` prints `knowledge/<topic>.json <id>: verify path "<p>" is ignored by git; commit a copy under a tracked path and verify that`, before and in place of the missing-path line for that path. Outside a git work tree the ignore test does not run. Inside one, every other failure of git is a named line and no verdict: `knowledge: verify paths not tested against .gitignore: <git fault>` for the `verify` paths, and `.houserules.json: workspaces path ".houserules/work" not tested against .gitignore: <git fault>` for the default location, where `<git fault>` is `git check-ignore failed: <git's first stderr line>` or `git check-ignore could not run: <the OS error>`. A path inside a submodule is no member of the answer (no ignore line of this repository covers it), and the other paths keep their verdicts. A path through a symlink is judged at the link's target when the target lies inside the install root, and at the link when it does not; a directory question about a symlink (`<link>/`) is judged the same way (Task 6 review, issue 1, and its fix round).
- The move of an install that tracks its workspaces: `update` cannot detect it (the kit named no location before) and prints nothing. The upgrade guide's batch-35 section gives the hand step: set `workspaces` to the folder or move it under `.houserules/work/`; for a folder outside `.houserules/`, add its line to `.gitignore` first; run `git rm -r --cached <folder>` and commit; for each `verify` path `check-knowledge` then names, commit a copy under a tracked path (for example `tests/fixtures/`) and point `verify` at it.
