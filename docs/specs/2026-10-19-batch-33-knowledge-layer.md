## 3. The layout (5.162)

```
knowledge/
  schema.json            delivered by update through a baseline (D3); no area enum (5.134, 5.143)
  areas.json             project-owned; the one list of areas (5.134)
  <topic>.json           the local pack: the project's own entries, in topic files as today
  overrides.json         project-owned: overrides by id and field, and exclusions by id
  archive/<topic>.json   as today, for local entries only
  packs/<pack>.json      one pinned copy per installed pack, in emit form
.houserules.json         schema, version, idPrefix, packs, ownedPaths, defaultBranch (optional),
                         renderers, baselines (paths only)
```

The rules of the layout:

- L1. Pack copy. `knowledge/packs/<pack>.json` holds the pack's `name`, `version`, `schema` (`houserules/pack@<semver>`, 5.117), `topics` (each topic it serves, with a title), `areas` (each area its entries use, with default globs, 5.134), and `entries`. An entry's topic is the first part of its id. A pack's ids each start with one of the topics it declares (F2, applied per topic). A pack name matches `^[a-z0-9-]+$`, the pattern of a topic name, and is never `local`, which `stats` uses for the local pack (section 4.3). The embedded pack schema (L6) carries the pattern. `pack add` and `pack upgrade` check the name of the file they read before they write anything, and refuse a violating name with one line that names it.
- L2. Pack names are unique among installed packs: one copy file and one pin key per name. `pack add` refuses a name that is already installed; `pack upgrade` moves an installed upstream pack (section 4.2, 5.166). `update` identifies the kit's packs by their source, never by their name, so it never overwrites an upstream pack that carries a kit pack's name.
- L3. Pins. `.houserules.json` `packs` maps each pack name to `version`, `source`, `sha256`, and `addedAreas`; a git source also records `commit`, the commit its tag resolved to, so a moved tag cannot change a pinned pack (5.164). `sha256` hashes the canonical serialization of the parsed copy (5.162: "the canonical parsed JSON"): compact JSON of the parsed value with every object's keys sorted, so neither a checkout's line endings (F6) nor a reformat that reorders keys fails the pin. Clarified 2026-10-19 at Task 1: `canonical_entry_bytes` keeps the parsed key order, which the plan's Review focus 1 showed is not canonical.
- L3a. The `source` of a pin has three forms. `kit`: the binary carries the pack, and `update` moves it. `file:<path>`: `pack add <file>` copied it; the path is relative to the install root. `git+<url>@<tag>#<path>`: the part after the last `#` is the file's path in that repository; in the rest, the last `@` splits the URL from the tag, so a URL such as `git+ssh://git@host/org/repo` keeps its own `@`. The tag must be a tag: `pack add` and `pack upgrade` resolve it with `git ls-remote --tags` and refuse, with one line, a ref that names no tag (a branch or a commit), because a pin is exact (`security-hygiene.exact-pins`). `commit` holds the commit the tag points to, peeled for an annotated tag (the `<tag>^{}` line of `git ls-remote`), never the tag object's own id.
- L4. Overrides and exclusions. `knowledge/overrides.json` holds `overrides` (an id and the fields it replaces; any field of the schema except `id`, 5.130; a field set to `null` removes it, F5) and `exclusions` (an id and an optional `reason`).
- L5. Validity of `overrides.json`. Each case fails `check-knowledge` with one line that names the id and the case: an override or exclusion of an id that no installed pack ships (after `pack remove`, or after a pack version drops the id, too); an override or exclusion of a local id; an override and an exclusion of the same id; two overrides of one id.
- L6. The schema that validates a pack copy or `overrides.json` is the binary's embedded schema for the schema id that the file declares (5.117, 5.126), never the project-owned `knowledge/schema.json`.
- L7. Reserved names. One constant names the `knowledge/` files that are not topics: `schema.json`, `areas.json`, and `overrides.json`. `load_base`, `archive`, and `install` read it. It replaces the hand-typed lists of F1. `check-knowledge` rejects a local topic named `overrides`.
- L8. One id, one source (5.110, 5.111). A conversion step keyed on the state "a local entry's id is shipped by an installed pack" runs on every `update` and on every `pack add`. When the local entry equals the pack entry, the step drops the local copy. When it differs, the step writes an override that carries each differing field (a field the local copy lacks is set to `null`). When `overrides.json` already holds an exclusion or an override of that id, the local copy replaces it, and the step prints one line for each item it replaced. The step removes an emptied topic file under L9. It also covers an archived local entry whose id an installed pack ships (after `pack add` of a pack that step 4 of section 5 left out): the entry becomes an override with `status: retired` and its other differing fields, and leaves the archive, as step 3 of section 5 does, so the id is never active and archived at once.
- L9. Removing a local topic file. A topic file goes only in the step that empties it (L8, or step 2 of section 5), which tests the state "the file holds at least one entry, and an installed pack ships every entry's id" before it moves the entries, and removes the file in the same step when the state holds. A file with `"entries": []` stays.
- L10. A retired pack entry is an override with `status: retired` (5.130). It stays in its pack copy. `archive` moves local entries only.
- L11. A topic's title is the local topic file's `title` when the project has one, else the title that the first pack in name order declares for that topic. `topics` sums the entry counts of every source, and `index --topic` lists every source's entries.
- L12. The marker gate (section 10) covers every file under `knowledge/`: the topic files, `packs/*.json`, `overrides.json`, and `archive/`.
- L13. The workflow-package pins of 5.140 are a `.houserules.json` key that batch 34 adds. No key of this layout takes that name.
- L14. `renderers` lists the enabled render targets besides the AGENTS.md renderer, which is always on (section 7). `init --target claude` writes `["claude"]`; `init` without it writes `[]`. The 1.x conversion writes `["claude"]` (5.113). `update` never adds a renderer: an install without the `claude` value keeps none. The approved layout (5.162) did not name this key; section 13 lists it as a controller call.

## 4. Packs (HR-182, HR-191)

### 4.1 The merged base

Every command reads one merged base: the local pack, each installed pack copy, and `overrides.json`.

- An entry of a pack copy, with its override applied, is active unless an exclusion names it or its effective `status` is other than `active` (`retired` or `superseded`, the statuses `archive` moves out of a local topic file). Clarified 2026-10-19 at Task 2: a retired or superseded pack entry stays in its copy (L10), so `for`, `standing`, `index`, `audit`, and `render` leave it out as they leave out an archived local entry; `get` prints it with its `overridden` field.
- `get` of an excluded id prints the pack entry with an `excluded` field that holds the reason, or `true` when there is none, and exits 0. `for`, `standing`, `index`, `audit`, and `render` leave an excluded entry out. A `get` of an id that is both active and archived prints the active entry (precedence: active source, then archive).
- `get` of an overridden id prints the effective entry and an `overridden` field that lists the replaced fields. `index` rows keep their shape.
- `check-knowledge` lists every override and exclusion in its output (issue 71 point 2, 5.106). The list does not fail the gate.
- `check-knowledge` fails an id that is active in one source and archived in another, with one line naming both files (HR-151(1)).
- `check-knowledge` fails an id that two active sources ship, with one line that names the id and both sources: a local entry and a pack entry (a hand-written local entry, until the next `update` or `pack add` runs L8), or two packs. It keeps 1.4.0's failure of one id in two local topic files (`check.rs:846`). Until the failure is fixed, every other command reads the local entry over a pack entry, which is the text L8 keeps, and the first pack in name order over another pack.
- A `see` link to an excluded id is not dangling: the pack ships the target, and the project chose to exclude it. A `see` link to an id that no source ships still fails.
- A pack copy that fails its `sha256` fails `check-knowledge` with one line that names the pack and says to put the change in `knowledge/overrides.json` (5.126).
- A pack copy whose `schema` major is newer than the binary reads fails every command with one line that names its format id, the running houserules version, and the format major to install a release for (5.126, 174): `<path>: pack schema "<id>" is newer than houserules <version> reads; install a houserules release that reads pack schema major <major>`. A copy whose `schema` has a newer minor of a major the binary reads is validated with the binary's embedded schema of that major, and keys that schema does not name are ignored: a minor adds only optional keys (D2, 5.117). See section 13, C13.
- A pin whose version differs from the binary's own version of a kit pack changes nothing by itself: every command reads the copy, and only `update` moves the pin (5.126).

### 4.2 Commands

- `houserules pack list` prints each installed pack: name, version, source, entry count, and the counts of its overrides and exclusions. It also lists each pack the binary carries that the install lacks.
- `houserules pack add <name>` installs a pack the binary carries at the binary's version. `houserules pack add git+<url>@<tag>#<path>` installs an upstream pack: it fetches that one file at that tag through the user's own `git` command, so any host and the user's git credentials work and no library is added (5.164). `houserules pack add <file>` copies a pack file the project already holds, for example a vendored file or a submodule. An HTTPS source is HR-200, not scheduled. Both write the copy in emit form (HR-162), write its pin, add its missing areas (section 6), and run the one-id-one-source step (L8). `pack add` refuses when another installed pack ships one of its ids (5.110), naming each id and the other pack. `pack add process` on an install with no tracker refuses with one line naming `--tracker` (5.149); batch 34 adds the tracker, so in batch 33 the check reads the presence of `backlog/` as the tracker (section 13, C7).
- `houserules pack remove <name>` deletes the copy and the pin, removes the areas it added under 5.134(3), and fails, changing nothing, while `overrides.json` names one of its ids. The line it prints names each such id.
- `houserules pack upgrade <name> <tag>` fetches like `pack add` and moves an installed upstream pack with a `git+` source to a new tag of the same URL and path (5.166). `houserules pack upgrade <name>` re-copies an upstream pack with a file source from its recorded path. It rewrites the copy and the pin (source, resolved commit, `sha256`), keeps every override and exclusion of `overrides.json`, applies section 6 to the areas of the old and the new version, and runs the one-id-one-source step (L8). It refuses, changing nothing, with one line for each case: a name that is not installed; a kit pack (the line names `houserules update`, 5.126, 5.165); another installed pack that ships one of the new version's ids (5.110); an override or exclusion in `overrides.json` that names an id the new version drops (L5), naming each id. It prints the old and the new version and the ids added and dropped. A change of source is `pack remove`, then `pack add`.
- Every `pack` command that changes a file then runs `render`, as `init` and `update` do, so the generated files never lag the knowledge base. It writes a file only when its content changes, so `pack add` of a pack that adds no area leaves `knowledge/areas.json` byte for byte. Clarified 2026-10-19 at Task 4. Also from Task 4's review: `pack list` shows a pin with no copy as installed, with the token `no copy` in place of its counts; a `git+` source whose URL is a relative local path is refused before any git call, with one line that asks for a `file://` or a remote URL, because a pin must name one repository from every directory; a render that fails after a pack write prints one line that says the pack files are written.
- Kit pack versions (5.165): each kit pack carries its own semver, starting at 1.0.0. Its version rises only when its content changes: major for a removed entry or a stricter check, minor for an added entry, patch for a wording change. A test pins each kit pack's content checksum to its version, so a content change without a version change fails CI. `update` therefore moves and reports only the pins of the packs that changed.

## 5. `update` and the 1.x conversion

Each step names its state on disk and in `.houserules.json`, acts only while that state holds, and runs on every `update` (5.148). Every state of steps 0 to 8 includes "`.houserules.json` has no `schema` key", which only a 1.x tree has: step 9 writes the key last, so no step of the conversion acts on a 2.0 install. Of this section's steps, L8 and the pack moves at the end of the section are the ones a 2.0 install runs.

On every install, 1.x or 2.0, `update` also keeps 1.4.0's sync of the files it owns over path baselines (`install.rs:1115-1141`, 5.100, D3 5.122). It writes each file as `init` writes it for the install (the id-prefix rewrite; a subdirectory install's workflow form) and restores a missing one. A file at its baseline is rewritten with the binary's content and rebaselined; a file whose bytes would not change is neither written nor listed, so a second `update` prints no `wrote` line; a modified file is kept and listed (`kept <file> (locally modified)`); a file in `ownedPaths` is never rewritten. Once baselined, the sync covers `knowledge/schema.json` and the install's seeded CI workflow under its baseline key (section 8). While `renderers` lacks `claude`, the sync writes none of the Claude files that `init` leaves out (section 7, C9). A second `update` changes nothing. `update` prints one summary: files rewritten, files kept, and hand steps.

The order of one `update` run: (1) step 0; when it stops, nothing else runs, the sync included; (2) steps 1 to 9, each while its state holds; (3) the pack moves at the end of this section, then L8; (4) the file sync, which so reads the `ownedPaths` and `renderers` that steps 1 and 7 wrote; (5) `render`. 1.4.0 runs its sync before the entry reconciliation (`install.rs:1115`, `:1147`); this batch moves it after the conversion.

"Changed" below has 1.x's meaning (`baseline::classify` Modified): the entry differs from its recorded baseline and from the binary's pack entry, or, with no baseline, from the binary's pack entry. An entry the adopter never changed is unchanged, even when the kit's text moved since its release. An override then carries each field that differs from the binary's pack entry.

The steps, in order. Steps 3 and 4 are tested before step 2 classifies any entry, so the states of steps 2, 3, and 4 are disjoint.

0. Reserved topic. State: no `schema` key, and `knowledge/overrides.json` exists (a 1.x topic named `overrides`). The conversion stops before any write, changes no file, and prints one hand step: move the entries of that topic to a topic with another name, then run `update` again (5.162(4)).
1. Overrides split. State: no `schema` key, and `.houserules.json` has an `overrides` key. Each id goes to `knowledge/overrides.json` under 5.123: a listed seeded entry that is present becomes an override that carries its differing fields, or nothing when it equals the binary's pack entry; a listed seeded entry that is absent becomes an exclusion. Each path goes to `ownedPaths`. An id of a topic that step 4 covers writes nothing to `overrides.json`, since no pack ships it there (L5). The step then removes the `overrides` key.
2. Seeded entries to packs. State: no `schema` key, and a local topic file that step 4 does not cover holds, or lost, an entry whose id a kit pack ships and that step 3 does not cover. 'Deleted' in 5.113 means absent with a recorded baseline, or listed in `overrides` (step 1). An absent entry with no baseline was never delivered (F4) and becomes a pack entry, not an exclusion. A changed seeded entry becomes an override (5.113); a deleted one becomes an exclusion; an unchanged one becomes a pack entry. An id that step 1 handled keeps step 1's result; step 2 only moves its entry out of the local file. Each such id becomes the hand step of 5.112 when a workflow requires it (batch 34 adds the requirement list). The state includes a project-only id that a 2.0 kit pack now ships (here `knowledge-base.cite-durable-refs`, HR-178): with no baseline, it is compared with the pack entry, as L8 does, so the stamped tree holds one source per id. Before it moves entries, the step tests L9's state on the file; when it holds, the step removes the file in the same step.
3. Archived seeded entries. State: no `schema` key, and `knowledge/archive/<topic>.json` holds an entry whose id a kit pack ships, for a topic that step 4 does not cover. An archived entry of a topic that step 4 covers stays in the archive as a local entry, since no pack ships its id there (L5). The entry becomes an override with `status: retired` and, when it is changed, its other differing fields (L10). The step removes it from the archive file, and removes an archive file it empties. Step 2 does not classify the id, so the id gets no exclusion.
4. `ownedPaths` topic files. State: no `schema` key, and `ownedPaths` lists `knowledge/<topic>.json` (a state the 1.x citation remedy can print). 5.123(3) forbids rewriting the file. The conversion installs no pack for that topic and writes no exclusion for it. A present file keeps every entry local; an absent file stays absent. The step prints one line naming `houserules pack add <pack>` as the way back.
5. Pins. State: no `schema` key, and a kit pack that step 4 does not cover has no pin, or has a pin whose copy is absent or does not match the pin's `sha256` (C20). The step writes the copy and the pin. It adds each area the pack declares and `areas.json` lacks, and records that area in the pack's `addedAreas`; an area that existed before the conversion is the project's own and goes in no `addedAreas` (section 6).
6. Baselines. State: no `schema` key, and `baselines` holds an id key. Every id-keyed baseline goes: the kit ids (46 here), whose pins replace them, and the non-kit ids (3 here). Path baselines stay (8 here).
7. Claude files. State: no `schema` key. `.claude/rules/standing-rules.md` is removed (5.129), and `renderers` is written as `["claude"]` (L14, 5.113). When a `CLAUDE.md` in the install root does not import `AGENTS.md`, the step lists the hand step "add `@AGENTS.md` to CLAUDE.md": without the import, the standing rules no longer reach Claude Code (F7). `check-knowledge` fails the same state with the same line (section 7).
8. D3, first time. State: no `schema` key. This step is the 1.x recognition of 5.142 only; the sync above delivers both files on every later `update`. The step covers `knowledge/schema.json` and the seeded CI workflow (5.142, 5.143): the binary carries each released content of the two files; the step applies the install's id-prefix rewrite to each and compares the result with the copy on disk. The knowledge schema is compared without `$defs.area`. A match is replaced with the 2.0 file and baselined. A schema with other changes loses only `$defs.area` and the `area` property's `$ref`; the edit is printed and the rest is a hand step. A schema path in `ownedPaths` is not rewritten; `update` lists removing `$defs.area` as a hand step. Any other copy is kept and listed as a hand step.
9. The `schema` key. State: no `schema` key. The step writes `houserules/install@2.0.0`, last.

The writer survives a stop between any two of its writes (C20). A tree whose `.houserules.json` has no `schema` key converts even when `knowledge/schema.json` is absent (C21).

Steps 0 to 9 are a pure function from a 1.x tree to the new layout, plus a writer. HR-193 (batch 37) reuses the function for its in-memory read of a 1.x merge base, which maps the layout only and keeps each entry's text from the merge base (5.151, 5.153). The function assigns entries to packs by id, using the id lists of the binary's packs and no text. An id that a 2.0 pack adds but the merge base lacks is absent from the merge-base rules.

D4 (5.133): this binary writes install schema major 2. On a tree whose install schema is missing or has a lower major, every command that reads the install prints one named line and exits 2: the gates `check-knowledge`, `check-backlog`, `check-commit`, `audit`, `validate`, and `render --check`, and also `render`, `get`, `for`, `index`, `topics`, `standing`, `list`, `batch`, `set`, `stats`, `archive`, `check-report-claims`, and `pack`. The session-start hook's `standing` then shows D4's line to the agent. `update`, `init`, and `files` run: D4 does not block them (C17). An install schema with a higher major than the binary writes is refused too, by every command but `files` (C22). D4's line names `houserules update`; when `.houserules.json` is absent, it names `houserules update --id-prefix <prefix>`, and `update` on a tree with `knowledge/` and no `.houserules.json` refuses without `--id-prefix`, so no remedy stamps `WI` on a project with its own prefix (HR-151(2)). D4 checks the tree under test only (5.151(2)). See section 13, C14.

Pack moves on a 2.0 install:

- `update` moves the kit packs' pins to the binary's versions, rewrites their copies, keeps overrides and exclusions, applies section 6, and prints one line per moved pin (5.126, 5.165). It never fetches a pack the binary does not carry.

## 6. Areas (5.134)

- `knowledge/areas.json` is the one list of areas, and the project owns it. The `area` enum leaves the knowledge schema. `check-knowledge` checks every active entry's area against the keys of `areas.json`; an archived entry keeps its area as plain text, unchecked.
- `pack add`, and an `update` that brings a new pack version, add each area the pack declares and `areas.json` lacks, with the pack's globs, and record it in the pack's `addedAreas`. They print one line per area. An existing area keeps the project's globs.
- `pack remove`, and an `update` in which a pack drops an area, remove an area only when a pack added it, no remaining pack declares it, and no active entry of any source uses it. They print each removed area with its globs. When another installed pack still declares a kept area, the record moves to that pack's `addedAreas` (the first in name order), so the area stays pack-added.
- The 1.x conversion records each area it adds in the adding pack's `addedAreas`, and no area that existed before it (section 5, step 5).
- A glob that `pack add` or `update` writes and that matches no tracked file is named in their output. `check-knowledge` does not fail on such a glob while a pack's `addedAreas` records the area and its globs equal a declaring pack's globs (C16).
- An area key `"agentsMd": false` turns off the area's directory AGENTS.md (5.134(6)).
- On an install that keeps `$defs.area` (5.143(3)), `check-knowledge` names the enum as the cause when a pack adds an area that the enum lacks.

## 8. The subdirectory install (HR-147, 5.135)

- Every command's default root is the nearest directory at or above the current directory that holds `.houserules.json`, searching no higher than the git top level; when none exists, the git top level.
- `init --dir <subdir>` installs there. `.claude/` and `.githooks/` live in the install root. The docs say to launch Claude Code in the install root.
- houserules never sets `core.hooksPath`. The commit-msg hook passes `--dir` with the install root, read from its own file path. The docs give both activations: `git config core.hooksPath <subdir>/.githooks`, or a one-line call from the existing hook manager.
- Every path a gate matches is relative to the install root, and a path outside the root is out of scope. git prints `diff --name-only` paths from the git top level, and `ls-tree -r --name-only` run in the install root prints them from the root (`spec-review-probe-subdir-paths.txt`). One function maps each git path list to install-root paths and drops the paths outside the root. `audit` (`changed_files`, `tree_files`), `check-commit`, `for`, and every check type (area globs, `files`, `if`/`then`, co-change, grep-absent, the per-commit checks) read the mapped lists. An install at the git top level maps every path to itself.
- In a subdirectory install, `check-commit` checks only the commits that touch the install root (the hook reads the staged files; `--from` reads each commit's changed paths) and prints one line that counts the skipped commits. An install at the git top level checks every commit. Clarified 2026-10-19 at Task 5's review: a commit is skipped only when it changes at least one path and none of them is under the install root, so an empty commit (and an empty index in the hook) is checked by both arms; a merge commit counts the paths of every parent diff; `--from` prints the count line on every run of a subdirectory install, `skipped 0 commits` included; the hook prints it only when it skips. `for` takes each path relative to the install root, as every gate does, and its help says so.
- The seeded CI workflow stays at the git top level. For a subdirectory install, `init` writes it with `working-directory: <subdir>` and a `paths` filter on `<subdir>/**`.
- Several installs in one repository (5.168). An install at the git top level keeps `.github/workflows/knowledge.yml`. A subdirectory install gets `.github/workflows/knowledge-<folder>.yml`, where `<folder>` is the install root's path from the git top level with each `/` replaced by `-`; its workflow `name` is `knowledge (<path>)`. It is the one file an install writes outside its root. Its baseline key is its path from the git top level in git's top-level pathspec form, `:/.github/workflows/knowledge-<folder>.yml`, so the key does not depend on the install root. An install at the git top level uses the same form, `:/.github/workflows/knowledge.yml` (D3). `init` writes and baselines it there; the path-baseline sync of section 5 rewrites it on every `update`.
- `init` refuses, changing nothing, with one line that names the other install: a workflow file name that another install already uses (for example `a-b` and `a/b`); an install root inside another install's root, or one that holds another install (section 13, C12). `init` in an existing install's own root is not a second install: as in 1.4.0, it seeds what is missing and keeps what exists.

## 16. Acceptance and the live run

- A fresh `init` in a scratch repository, then `pack list`, `pack add` of an upstream pack, an override, an exclusion, and `pack remove`: every gate passes, and each refusal of section 4.2 prints its line.
- `pack add` of a git source on a local bare repository with a tag, then a moved tag: the pin keeps its commit and checksum, and every gate passes with no network.
- `pack upgrade` of that pack to a second tag that adds one id and drops one: with an override of the dropped id it refuses and changes nothing; after the override goes, it moves the pin, keeps the other overrides, and prints the added and dropped ids. `pack upgrade` of a kit pack and `pack add` of the installed name each refuse with their line.
