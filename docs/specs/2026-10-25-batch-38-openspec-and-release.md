## 3. The `openspec` intent adapter (HR-209)

The adapter implements batch 37's contract (batch-37 spec 4.9): it reads files of the tree at a given commit, `--head` unless a rule says otherwise, and runs no tool. Each field reads each file as the OpenSpec 1.15.0 function that section 2 names reads it.

1. **The root.** The `openspec/` folder of the install root (batch-37 spec 4.1 keeps every path outside the install root out of scope, so an OpenSpec root above a subdirectory install is not read; reversal: an adopter with that layout). It has a planning shape when `openspec/specs/` or `openspec/changes/` is a folder without `.openspec-store/store.yaml`. Without a planning shape, a `store:` key in `openspec/config.yaml` (else `openspec/config.yml`) makes it a store pointer, which the adapter does not follow. The Why, section, and requirement readers normalize a file first, as OpenSpec's `MarkdownParser` does: a leading UTF-8 BOM removed, CRLF and CR turned into LF. The title reads the raw `proposal.md`. The task reader reads each file raw and splits it on LF, as `task-progress.ts` does, so a CR-only file is one line (task review, round 0). A symlink or a submodule of the tree is no file of a change; OpenSpec reads through a file link, but at a commit the link holds only its target's path (a departure, kept; reversal: an adopter whose changes hold links).
2. **Found by, and the ref.** A changed path of the range (a deleted path by its old path, a renamed one by both, batch-37 spec 4.7) under `openspec/changes/<name>/` with `<name>` not `archive` is the active change `<name>`; under `openspec/changes/archive/<name>/` it is the archived change `<name>`; a `<name>` that starts with `.` is no change. The `ref` of an intent is OpenSpec's id: the folder name of an active change, or the full folder name of an archived one (for example `2026-01-02-old-change`, the id that `openspec validate --archived` prints). An active change whose folder no longer exists at the head (archived in the range) resolves to the archived folder `<YYYY-MM-DD>-<name>` with the latest date; a found change that has neither its folder nor an archived folder at the head (deleted, or renamed in the range, by its old name) gives no intent; a change renamed in the range is found by its new name. Named and found intents are deduplicated by source and `ref`. A named `openspec:<id>` (the bundle's `Intent:` line, `--intent`, or a trailer of 5.1) resolves to `changes/<id>/` (never `changes/archive/` itself: `archive` is no change id), else `changes/archive/<id>/`, else the archived folder `<YYYY-MM-DD>-<id>` with the latest date.
3. **Fields.**
   - `title`: the `extractTitle` rule over the whole `proposal.md`, trimmed; the `ref` when the file is missing, nothing matches, or the title reads `proposal` in any case.
   - `why`: the first heading of any level whose title is `Why` (case-insensitive) outside fences, in document order; its lines to the next heading of the same or a higher level, subsections included, newlines kept, trimmed, cut to 1,000 characters; `null` when absent or empty.
   - `tasks`: `{done, total}` over the tracked files. The schema name is the config's `schema`, else `spec-driven`, when the change has no `.openspec.yaml`; when it has one, its `schema`, and a `.openspec.yaml` that fails to parse as YAML, lacks a non-empty `schema`, or names a schema that neither the tree nor 1.15.0's built-ins hold sends the count to the `tasks.md` fallback, as OpenSpec's throw does. The schema file is `openspec/schemas/<name>/schema.yaml` of the tree (a project-local `spec-driven` included), else the built-in `spec-driven` of 1.15.0 (its `tasks` artifact generates `tasks.md`); a user-level schema is outside the tree and counts as unresolved. The tracked artifact is the one whose `generates` equals `apply.tracks`, else the one with id `tasks`; its `generates` is a glob relative to the change folder, matched through `rules::glob::compile` (`*` stays inside a path segment; `?`, `**`, `[...]`, and `{a,b}`), and a file or folder whose name starts with `.` matches only a pattern segment that starts with `.`, as OpenSpec's `dot: false`; a brace range such as `{1..3}` and an extglob such as `+(a|b)` match as literal text (OpenSpec expands them; reversal: an adopter's schema uses one). With no resolved schema, no tracked artifact, or no matched file, the change's top-level `tasks.md` counts. Every line of each file that matches `TASK_LINE_PATTERN` counts, fences included; `x` and `X` are done. `null` when no file was read. A config or `schema.yaml` that does not parse as YAML counts as absent, as `resolveSchemaForChange` treats an unreadable config. A `schema.yaml` that OpenSpec's schema validation refuses (one without `version`, for example) counts as unresolved. A `generates` glob that does not compile matches no file, as picomatch's never-matching pattern does, so the `tasks.md` fallback counts; no line names it. A brace list expands before the dot rule applies to each segment, as picomatch expands it first (task review, round 0). A tasks glob that OpenSpec 1.15.0 refuses with its own error (an expansion past 1,024 patterns, braces nested more than 16 levels, an alternative that leaves the change folder) counts the `tasks.md` fallback, where OpenSpec gives no count (a departure, kept: a schema never stops `evidence`, as a trailer never does (5.2), and OpenSpec refuses such a schema on every command, so no working tree holds one; reversal: an adopter's tree that OpenSpec accepts reaches the case; Task 1 fix-diff review). A backslash in a tasks glob is no path separator, where OpenSpec turns it into one first (a departure, kept: a path of a git tree holds no backslash separator; reversal: an adopter's schema writes a Windows path; Task 1 fix round 2).
   - `requirements`: `{added, modified, removed, renamed, total}` over each file named `spec.md` at least one folder below the change's `specs/`, skipping names that start with `.`. Level-2 sections outside fences whose title is `ADDED Requirements`, `MODIFIED Requirements`, `REMOVED Requirements`, or `RENAMED Requirements` (case-insensitive) hold the entries: in ADDED and MODIFIED each requirement header outside fences, in REMOVED each header or bullet, in RENAMED each `FROM:` line followed by a `TO:` line with no `FROM:` between. `total` is the sum; `null` when no file holds one of the four sections. Two departures from `openspec show`, each kept: without a delta section, `show` counts the What Changes bullets of the proposal, and the adapter gives `null` (best case of the rejected option: a count for the one legacy-format change of the corpus; the prose format predates delta specs; reversal: an adopter whose changes use it); for a proposal without Why or What Changes, `show` exits 1, and the adapter still gives the title, tasks, and counts it can read (a reviewer sees what the change holds; `why` is `null`).
   - `validation`: section 4. `artifacts`: the change folder's files at the commit, as paths relative to the install root, sorted.
4. **The patterns,** compiled with `regress` and copied from the v1.15.0 source: the title `^#\s+(?:Change:\s+)?(.+)$` (`im`); a heading `^(#{1,6})\s+(.+)$`; a level-2 section `^(##)\s+(.+)$`; a requirement `^###\s*Requirement:\s*(.+)\s*$` (`i`); a REMOVED bullet ``^\s*[-*+]\s*`?###\s*Requirement:\s*(.+?)`?\s*$``; a RENAMED pair's lines ``^\s*[-*+]?\s*FROM:\s*`?###\s*Requirement:\s*(.+?)`?\s*$`` and the same with `TO:`; a task `^\s*(?:[-*+]|\d{1,9}[.)])\s*\[(?:\s*([^\]\s]?)\s*\](?![([])|\s+\])\s*(.*)`; a change id `^[a-z0-9]+(?:-[a-z0-9]+)*$`; the fences of `code-fence.ts`, which mask headings, sections, and requirements, not the title and not tasks. This fence rule is OpenSpec's and differs from the bundle section's (batch-37 spec 7.1); each mirrors the reader it serves.
5. **The adapter's lines** (batch-37 spec 4.9's form; `bundle check` prints them after `intent openspec:<id>: `): `no openspec/ folder at the head`; `the OpenSpec root points at a store, which houserules does not read`; `an OpenSpec change id is kebab-case: lowercase letters, digits, and single hyphens`; `no OpenSpec change with that id at the head, active or archived`.
6. **Configuration.** `review.intent.sources` accepts `openspec`; the line of an unknown source becomes `"<source>" is no intent source; use one of: work-item, file, openspec`.
7. **Batch 37's table.** The `openspec` column of batch-37 spec 4.9 was amended during batch 37 (243c88ac on `main`) to the rules of this section.

## 4. The validation capture

1. `evidence --validation <file>` and `record write --validation <file>` read a capture file (`houserules capture`) of an `openspec validate --json` run; `docs/openspec.md` gives the command: `houserules capture --out <file> -- sh -c 'openspec validate --all --json 2>/dev/null'`. The capture's header binds it: its `head` must be the commit of `--head` and `dirty` must be `false`. Its output must be one JSON document of section 2's shape with `version` `"1.0"`. Else the input is refused with the line `evidence: --validation <path>: <reason>` (`record:` for `record write`), where `<reason>` is one of `cannot be read (<os error>)`, `is no capture (<the line of capture's reader>)`, `ran outside a git work tree`, `ran at <head7>, not at <head7>`, `ran in a dirty work tree`, `holds no JSON (<serde line>)`, or `is no openspec validate document (version "1.0" with items)`. A refused capture never stops a command: `evidence` and `record write` print the line on stderr, keep every `validation` `null`, and exit as without the flag, as batch-37 spec 8.3 treats a tool that cannot run. The run's own exit (1 when an item fails) is no error. The documented run validates active changes only: an archived change (3.2) has no item, and its `validation` is `null`; `docs/openspec.md` says so.
2. Each `openspec` intent takes the item whose `type` is `change` and whose `id` equals its `ref` (a capability of the same id is another item): `validation` is `{tool: "openspec", ok: <valid>, summary}`, where `summary` is `no issues`, `1 issue`, or `<n> issues`, counting every issue of every level. An intent with no item keeps `validation: null`. Other sources ignore the capture.
3. **CI.** Both units gain the input `validation` (default empty): a path, relative to the install, that `setup` writes with the command of 4.1; when the input is set and the file exists, `evidence` and `record write` get `--validation <path>`; a set input whose file does not exist prints one notice, `houserules: the validation input names <path>, which does not exist, so this run passes no validation capture` (`<path>` joined to the install's folder as `${HOUSERULES_DIR%/}/<input>`), and passes no flag (Task 5's open reading, ruled before its tests). The packet prints batch 37's line `Validation: openspec <ok|failed>: <summary>`.

## 5. Spec and session links (HR-190)

1. **Trailers.** `evidence`, `record write`, and `audit` read the trailers of each commit of the range by `rules::trailers::parse`: `Intent: <source>:<ref>`, which names an intent as the bundle's line does, and each key that `review.sessions.trailers` lists (default `["Entire-Checkpoint"]`, 267(2)), matched case-insensitively as git matches trailer keys, whose value is a session reference. Each named `<source>:<ref>` counts once across trailers, the bundle, and `--intent`.
2. **A trailer never stops a command.** An `Intent:` value that is no `<source>:<ref>`, or whose source is no adapter, prints as an unresolved intent block with the adapter's line of batch-37 spec 4.9 (and the JSON `unresolved` key), and the command exits 0 for it: a commit's text never makes `evidence` or `record write` exit 2. Trailer intents of a source that `review.intent.sources` does not list sort after the configured adapters, by source and then by ref.
3. **The packet.** `### Size and links` gains `Sessions: <sha7> <key>: <value>, ...` (each value cut to 100 characters and printed as batch-37 spec 4.8 says, at most 20 entries, then `... and <k> more`), or `Sessions: none`; the line is bounded, so it stays out of the cut order of batch-37 spec 5.8. `houserules/evidence@1.1.0` adds `sessions: [{commit, trailer, value}]` in commit order.
4. **The record.** `houserules/change-record@1.1.0` adds `links.sessions` (the same entries) and `links.sessions_more` (the count past 20, or absent), and its `evidence` part leaves `sessions` out, as it leaves out `intent`, so the list lives once; step 7 of batch-37 spec 8.4 cuts it to 20; the minimal record of step 8 holds no session.
5. **The two checks (267(1), 272).** Two check types of the knowledge schema, deterministic, without `covers`:
   - `intent-required`: `{"type": "intent-required", "if": [<globs>], "sources": [<spec adapters>]?, "exempt_subjects": [<regexes>]?, "level": ...}`; `if` is required. `sources` takes `file` and `openspec` only (default both); `work-item` is no spec. The check's paths are the paths of batch-37 spec 4.2 for the range (a deleted path by its old path, a renamed one by both), less each path that only exempt commits change: each non-merge commit of the range contributes its diff against its first parent, a merge commit contributes nothing, and a commit whose subject matches a regex of `exempt_subjects` contributes nothing. When no such path matches `if`, the check does not apply to the change (it counts among the deterministic checks that did not apply, batch-37 spec 5.5). Otherwise it fails when no intent of `sources` resolves for the range, by the `Intent:` trailers of 5.1 and the changed paths that the adapters of `sources` find.    - `intent-resolves`: `{"type": "intent-resolves", "level": ...}`. It fails for each `Intent:` trailer of the range whose intent resolves neither at `--head` nor at the merge base (the adapter reads the tree at that commit), one line each: `<sha7> Intent: <source>:<ref>: <the adapter's line>`. A range with no `Intent:` trailer passes, with the evidence `no Intent: trailer in the range`.
   - `check-knowledge` gives each its lines: a `covers` on either type prints the existing line `check "<type>" cannot declare "covers": it reads no file`; a missing `if` prints the existing line of a required field; `<file> <id>: check sources "<x>" is no spec adapter; use file or openspec`; `<file> <id>: check exempt_subjects is not a valid regex (<message>)` (the existing regex line).
   - No pack entry uses either check (272). `docs/openspec.md` and the migrating-knowledge skill show one example entry of each.

## 19. The faster loop in the reference workflow (HR-260; design.md 280 to 283)

The kit ships the loop that this repository runs under design.md 280 and 281, and the two body sentences of 282, so that an adopter of the reference workflow gets them with 2.0.0. The text below states the rule that each kit file carries; the task writes each rule in the kit's style (ASD-STE100) and pins its sentences whole.

1. **Targeted tests in a task (280(1)).** The implementer template: while iterating, run the focused test; before commit, run the tests of the files the task changes (each test file it adds or changes, each test file that runs a command or module whose source it changes) and every other gate of the brief; the report names the targets. 2. **Open readings (280(2)).** The implementer template: a reading that the spec or the brief leaves open and that a test would pin is a question before that test is written: stop, name the reading and its choices, return NEEDS_CONTEXT. ## 20. Two first-run fixes (design.md 289)

1. **The `next:` line of `init` and `update`.** When the install root's git index holds at least one file and the command wrote at least one file that git does not track, the line reads `next: git add <paths> && houserules check-knowledge && houserules check-backlog`, where `<paths>` are the distinct first path components of the untracked files the command wrote, relative to the install root, sorted, separated by one space. The index is the one that `git ls-files` lists below the install root, as the dead-glob gate reads it. A file that git ignores is no untracked file: `git add` refuses an ignored path, and the line would stop. The files that the command wrote are the ones that its writers record: every write of `init` and `update` goes through one function that notes the path, and the writers leave a file that already holds the bytes alone, so such a file is no recorded write. The line opens no other file and reads no file's bytes; one `git ls-files` call, restricted to the recorded paths, names those that git neither tracks nor ignores. A path that a POSIX shell needs quoted is quoted (`shell::quote`). Otherwise the line stays `next: houserules check-knowledge && houserules check-backlog`. The dead-glob gate of `check-knowledge` is unchanged.
2. **An unknown batch.** `check-backlog` on the JSON tracker reports each item whose `batch` is a number that no record of `backlog/batches.json` or `backlog/archive/batches.json` holds, with one line that names the item file, the item id, and the batch, and exits 1. The line reads `<item file> <id>: batch <n> is not in backlog/batches.json or backlog/archive/batches.json`. `check-backlog` prints it on stderr beside its other errors, after the `see` findings of the same item. It judges the items of `backlog/items/` and no archived item, as `check-backlog` judges no other cross-file invariant of an archived item.
3. **Acceptance case 15.** In a repository with one commit, `init` prints the `git add` form of the line; running that line exits 0 for both checks. In a repository with no commit, `init` prints the old line. A backlog with an item of an unknown batch fails `check-backlog` with the new line; the same item with a known or archived batch passes. The upgrade guide names the new `check-backlog` red with its remedy.
