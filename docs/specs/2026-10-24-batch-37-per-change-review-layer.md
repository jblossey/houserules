## 4. The change analysis that the commands share

One module computes, for `--base` and `--head` (default `HEAD`), the facts that `evidence`, `route`, `bundle check`, and `record write` read. The audit rows come from one of two sources: `--audit <file>`, an `audit --json` result of the same range (its `base` and `head` must resolve to the same commits, else exit 2 with `<file> is the audit of <b7>..<h7>, not of <b7>..<h7>`), or an audit run in process, as `audit` runs it. The CI units run the audit once per job and pass the file (10), so the packet and the route read the same rows. `bundle check` and `route --no-audit` read no audit rows.

1. **The range.** The merge base of `--base` and `--head`, as `audit`'s three-dot range. When `--base` is git's empty tree (`record write` of a root push, 8.5), the range is every commit reachable from `--head`, diffed against the empty tree, and its audit rows audit that same range: every path of `--head`. Any spelling of the empty tree that git resolves to its object name counts. Paths are relative to the install root. A path outside the install root is out of scope, with one exception: the CI files that wire this install (the seeded `.github/workflows/knowledge.yml` or `knowledge-<folder>.yml` of 5.168, a file that `houserules ci write` created, and the file that `review.ci.files` names, 6.1) are rule sources for 6.2(1) and 4.5, and the packet lists them with their top-level path.
2. **The diff.** `git --attr-source=<git's empty tree> diff -M --no-relative --diff-algorithm=myers --inter-hunk-context=0 --src-prefix=a/ --dst-prefix=b/ --no-color --no-ext-diff --no-textconv -U0` and the same with `-z --numstat`, run with `LC_ALL=C`, `-c core.quotePath=false`, and `-c core.attributesFile=`, so that neither user configuration nor the request's own `.gitattributes` (a `-diff` attribute turns any text path into `binary`, `spec-review-r3-probe-gitattributes.txt`) can change the parsed text (2). Every other git setting or attribute file that changes the kinds, the counts, the ranges, or the paths of the parsed text is pinned by its own option or environment variable in the same way, each with a test (`diff.algorithm`, `diff.interHunkContext`, and `core.attributesFile` are the ones that `review4-git-config-probe-output.txt` shows), and every other `git diff` of the analysis carries the options of this list that apply to it. One input stays: no git option turns off the repository's own `.git/info/attributes`, so it is an input of a local run; a CI clone holds none (design.md 255). `--attr-source` needs git 2.41 or later (`review4-relnotes.txt`); with an older git, each command of 4 exits 2 with `<command>: git <version> is older than 2.41, which --attr-source needs`. Each changed path has one kind:

   | Kind | Git form | Changed lines (4.4) | Diff size (4.3) | Packet line (5.3) |
   |---|---|---|---|---|
   | `text` | hunks | added + deleted | added + deleted | `lines 2, 5-7; deleted after line 4: 2 lines` |
   | `deleted` | `+0,0` hunk | deleted | deleted | `deleted, lines 1-2 of the old file` |
   | `renamed` | rename, no hunk | 1 | 0 | `renamed from <old>` |
   | `empty` | an empty file added or deleted | 1 | 0 | `empty file added` or `empty file deleted` |
   | `binary` | `Binary files ... differ` | 1 | 0 | `binary` |
   | `mode` | `old mode`/`new mode`, no hunk | 1 | 0 | `mode only` |
   | `symlink` | mode `120000` | added + deleted | added + deleted | `symlink, lines 1-1` |
   | `submodule` | mode `160000` | 1 | 0 | `submodule` |

   A hunk of a `text` path has a new-side range (`lines <start>-<end>`, or `<start>` for one line) or, when it only deletes lines (`+<n>,0`), the form `deleted after line <n>: <k> lines`. A rename with edits is `text` under its new path and names its old path. A deleted path is listed and matched by its old path.
3. **The diff size.** The sum of the diff-size column over the paths that match no glob of `review.diffExclude` (default: none). An excluded path leaves the diff size and both sides of the uncovered share; the packet lists it as excluded.
4. **Coverage (design.md 229).** A check counts as coverage only when its entry's `check` declares `covers: true` (a new optional boolean of the knowledge schema, default `false`; a minor addition). `check-knowledge` fails `covers` on a `commits` or `report-field` check, which read no file. A changed path is covered when a covering check of the audit package reads it (`files` for `grep-absent`, `diff-append-only`, `durable-sha`, and `runner`; a runner check with no `files` reads every file; `if` or `then` for `co-change`) and its row's result is `pass` or `warn`. A check reports one result per row, not per file, so this spec reads 229's "on that file" per row: a failed covering row leaves every path it read uncovered, and lists the rule under Failed. The uncovered share is the uncovered changed lines over the changed lines, `0` for a change with no changed line. No kit pack entry declares `covers`.
5. **The rules hashes.** For a commit `c`, the SHA-256 of the output of `git -c core.quotePath=false ls-tree -r --full-name <c> -- :/<install>/knowledge :/<install>/.houserules.json <the CI files of 4.1 as top-level pathspecs>` (`<install>/` empty for a top-level install), run from the install root with `LC_ALL=C`. The CI files are those of `c`'s own tree: `review.ci.files` of `git show c:<install>/.houserules.json`, the seeded workflow by the install path, and each file whose first line at `c` is `ci write`'s comment; so the bytes depend only on the commit and the install path (`spec-review-r3-probe-ruleshash.txt`). An empty output at the head is an error (`no rule sources at <c7>`). An empty output at the merge base (the first request of a fresh install, a root push) is the value `null`, with `merge_base_rules: "absent"`; `record show` then checks only the head.
6. **The work items.** The `Work-Item:` trailers of the range's commits, in commit order, without duplicates; each resolves through the tracker as in `audit`.
7. **The areas of a change.** Every path of 4.2 (a deleted path by its old path, a renamed path by both) maps to the areas whose globs match it (`knowledge/areas.json`); a path that matches no area is in no area. The route reads this map, not `audit`'s `area_files`.
8. **Untrusted text.** Every value that comes from the repository, a tool, or a request description (a path, an evidence text, a work-item id, an argv, an intent's title and why) prints in Markdown inside a code span whose fence is one backtick longer than the longest backtick run of the value; a value with a control character prints as a JSON string inside that span; a multi-line value (a why) prints as a fenced block whose fence is one backtick longer than any backtick run in it. So a `<!--` or a heading in a value never changes the comment's layout.
9. **The intent (design.md 243, HR-246).** The intent of a change is what it was meant to do, as a spec workflow, a plan, or a work item records it. It joins the packet, the record, and the bundle into one report with the rule trace.
   - **The contract.** A spec adapter reads files of the tree at `--head` (and the range's changed paths and trailers) and, for work items, the tracker as `audit` reads it; it runs no spec tool, so a gate never depends on another tool's install (5.116, C13). It returns zero or more intents, each `{source, ref, title, why, tasks, requirements, validation, artifacts}`: `source` is the adapter's name; `ref` its id for the intent (a change id, a folder, a path, a work-item id); `title` and `why` texts or `null`; `tasks` `{done, total}` or `null`; `requirements` `{added, modified, removed, renamed, total}`, each a count or `null`, or `null`; `validation` `{tool, ok, summary}` or `null` (filled only from a spec tool's JSON output file that a caller passes, never by running the tool; the flag that passes the file is batch 38's, so every adapter of this batch leaves it `null`); `artifacts` the paths the adapter read.
   - **Which adapters run.** `review.intent.sources` (6.1) lists the adapters to run, in order; default `["work-item"]`. The bundle's `Intent: <source>:<ref>` line (7.1) names one intent directly, and the adapter of that source resolves it, whatever the config.
   - **The adapters of this batch.** `work-item`: one intent per work item of 4.6, with `ref` the id, `title` the tracker's title, and the rest `null` (with no tracker, none; a tracker that cannot be reached gives `title: null`). `file`: `Intent: file:<path>`, or each changed path that matches a glob of `review.intent.files` (for example `docs/plans/*.md`); `title` is its first `# ` heading, `why` the first paragraph after it, cut to 1,000 characters, `tasks` the counts of task-list lines, after any leading spaces and a list marker `-`, `*`, or `+`, of `[x]` or `[X]` and of `[ ]`, `requirements` and `validation` `null`.
   - **The adapter's lines.** A named intent that does not resolve gives one of these lines, which `bundle check` prints after `intent <source>:<ref>: ` (7.3); `evidence` exits 2 on an `--intent` whose source is no adapter (5.1): a text that is no `<source>:<ref>` gives `an intent is written <source>:<ref>`; a source that is no adapter gives `"<source>" is no intent source; use one of: work-item, file`, the wording of the config check of 6.1; a `file` path that is not relative to the install gives `the path must be relative to the install, with no empty, . or .. folder`; a `file` path with no regular file at `--head` gives `no regular file at that path at the head`; a work item that the tracker does not hold gives `the tracker holds no such work item`. A named work item in an install with no tracker, or with a tracker that cannot be reached, resolves to its intent with `title: null` and gives no line, as 7.3 treats an unresolved work item with no tracker. A failure that is not the named intent's own (the marker, the tracker's command, git) is no adapter line: the command exits 2 with it.
   - **The contract fits the spec workflows.** The table shows each field for the two workflows that batch 38 and HR-210 add; neither needs a field that the contract lacks:

## 5. `evidence` (HR-185)

1. `houserules evidence --base <ref> [--head <ref>] [--audit <file>] [--review <file>] [--intent <source>:<ref>] [--score <s>] [--out <file>] [--json <file>] [--dir <dir>]`. It prints the Markdown packet to stdout, or writes it to `--out`; `--json` also writes the `houserules/evidence@1.0.0` document. `--intent` names an intent as the bundle's line does (the CI units pass the bundle's line). It exits 0 whatever the audit's verdict; it exits 2 on the audit's setup errors, an `--audit` file of another range or that does not parse as an audit result, a `--review` file that does not parse as a review deliverable, an `--intent` whose source is no adapter (`evidence: --intent <source>:<ref>: <the adapter's line of 4.9>`), a failure of 4.9 that is not the named intent's own, a `--score` outside 0 to 1 (`evidence: --score <s> is outside 0 to 1`), a `--score` with neither threshold configured (the line of 6.2, rule 7), and an unwritable `--out` or `--json`.
2. The Markdown starts with the marker line `<!-- houserules:evidence <install> -->` (`<install>` is the install path relative to the git top level, `.` for a top-level install), then `## houserules evidence`, then one line: `Range <base7>..<head7> (merge base <mb7>) · rules <hash12> · route <route>`, where `<hash12>` is the first 12 hex digits of the head rules hash (4.5) and `<route>` is the route that `evidence` computed. The `report` job (10.1) inserts one line after the marker line, `Applied route: <route> (computed <r>, floor <f or missing>)`, at most 120 characters, so the posted comment names the route that the label and the status carry.
3. `### Intent (<n>)`, which follows the uncovered surface of 5.4 in the output (issue 65 puts the uncovered surface first): one block per intent, in adapter order: `<source> <ref>: <title>`, then `Why:` and the why, `Tasks: <d> of <t> done`, `Requirements: +<a> ~<m> -<r> renamed <n> (total <t>)` (a `null` count prints `?`), `Validation: <tool> <ok|failed>: <summary>`, each line only when its field is not `null`. No intent prints `None recorded.` A named `--intent` of an adapter that does not resolve prints its block as `<source> <ref>: <the adapter's line of 4.9>` with no other line, and the command exits 0 for it.
4. `### Uncovered surface (<u> of <n> changed lines)`: one item per uncovered path in path order, `<path>: <packet line of 4.2>` with the path as 4.8 prints it; then the line `Coverage is per file: a file is covered when a check that declares covers: true read it.` A change with no uncovered path prints `None.`
5. `### Failed (<n>)`, `### Warned (<n>)`, `### Proven (<n>)`: each deterministic row with result `fail`, `warn`, or `pass`, `` `<id>`: <evidence> ``; a fail that `audit --sanctioned` booked keeps its `(sanctioned: <ref>)` text, which reaches the packet only through `--audit`. `### Judged only (<n>)`: each judged row, `` `<id>`: <verdict> `` and the evidence of the `--review` file's `rule_adherence` row of that id, or `no verdict recorded`; a review result `pass`, `fail`, or `warn` is the verdict, any other value prints `open`. Then one line: `<n> deterministic checks did not apply to this change.` Each evidence text is cut to 300 characters with `...` and prints as 4.8 says.
6. `### Size and links`: `Diff: +<a> -<d> lines in <f> files` (plus `; <x> files excluded by review.diffExclude` when any), and `Work items: <ids>` (each id cut to 100 characters) or `Work items: none`.
7. `### Route`: `<route>`, then the reason lines of 6.3 at that route.
8. Order and bytes: every list sorts by path or by id (intents by adapter order, then `ref`); no time, no environment value, and no absolute path enters the output. The Markdown is at most 60,000 characters: when it would be longer, these are cut in this order, each to the items that fit, until it fits: Uncovered, Proven, Judged, Warned, Failed, the Route reason lines, the Work items list (to its first 50 ids), and the Intent blocks (each why first cut to 300 characters); each cut list ends with `... and <k> more`; the counts in the headings stay. The fixed lines and the headings take under 2,000 characters, so the cut always reaches the cap.
9. The JSON document holds the same content uncut: `schema`, `install`, `base`, `head`, `merge_base`, `intent` (the list of 4.9, in the order of 5.8; a named intent that does not resolve is an entry with its `source` and `ref`, every other field of 4.9 `null` (`artifacts` empty), and `unresolved`: the adapter's line of 4.9, a key that a resolved intent does not carry), `rules` (`merge_base_hash` or `null`, `head_hash`, `packs`: the packs that the marker at `--head` pins, read from git, sorted by name, each `{name, version, sha256}`), `diff` (`files`, `added`, `deleted`, `lines`, `excluded`), `uncovered` (`lines`, `total_lines`, `share`, `paths` with `path`, `old_path`, `kind`, `ranges` (each `{"start": s, "end": e}` or `{"after": n, "deleted": k}`), and, for the kind `empty` only, `empty`: `added` or `deleted` (absent for every other kind)), `failed`, `warned`, `proven`, `judged` (`id`, `verdict` or `null`, `evidence`), `skipped`, `work_items`, and `route` (6.4).

## 6. `route` (HR-186)

### 6.1 Configuration

`.houserules.json` gains the optional key `review` (an addition to the install layout, `houserules/install@2.3.0`):

```json
"review": {
  "diffExclude": ["Cargo.lock"],
  "route": {
    "default": "owner-review",
    "warn": "owner-review",
    "areas": { "docs": { "route": "auto-merge-eligible", "maxDiffLines": 200, "maxUncoveredShare": 0 } },
    "paths": [ { "glob": "crates/houserules/src/install/**", "route": "senior-review" } ],
    "ownerScore": 0.5,
    "seniorScore": 0.8,
    "sampleRate": 0.1
  },
  "bundle": {
    "budgets": { "light": 400, "standard": 1500 },
    "exemptAuthors": ["dependabot[bot]"],
    "exemptBranches": ["release-please--*"]
  },
  "intent": { "sources": ["work-item", "file"], "files": ["docs/plans/*.md"] },
  "ci": { "files": [".github/workflows/ci.yml"] },
  "record": { "maxBytes": 65536 }
}
```

The numbers above are an example; houserules ships no number (issue 58, point 3). An area or a path with `auto-merge-eligible` must name `maxDiffLines` and `maxUncoveredShare`, and the config must name `sampleRate` (0 to 1) then. `review.ci.files` names the project's own CI files that call houserules (rule sources, 4.1). `check-knowledge` fails, each with one line naming the key: a route value outside the three, an area that `knowledge/areas.json` does not define, an invalid glob, a missing threshold or `sampleRate`, a share, rate, or score threshold outside 0 to 1, a `review.route.default` or `review.route.warn` of `auto-merge-eligible` (design.md 257: a change is auto-merge-eligible only through an area or a path entry that names both limits), a negative number, an intent source that is no adapter of this binary, and a `maxBytes` below 8,192. The migrating-knowledge skill asks the owner for each number (7.6).

### 6.2 The decision

The route is the highest of these, in the order of 3. Rules 1, 4 and 6 (the configured route and `maxDiffLines`), 5, and 7 read no audit row; they form the tool-free floor that `route --no-audit` computes (design.md 242).

1. **Rule sources.** A changed path of the install's `knowledge/`, its `.houserules.json`, or a CI file of 4.1: `senior-review`. No configuration lowers it (5.151(3)).
2. **Failed rows.** A deterministic row with result `fail` that `audit --sanctioned` did not book: `owner-review`.
3. **Warned rows.** A deterministic row with result `warn`: `review.route.warn` (default `owner-review`).
4. **Areas.** Each area of 4.7 that holds a changed path: the area's `route`, else `review.route.default`, else `owner-review`. An area at `auto-merge-eligible` keeps it only while the diff size is at most its `maxDiffLines` and the uncovered share at most its `maxUncoveredShare`; past either, it gives `owner-review`. The floor reads the configured route and `maxDiffLines` only.
5. **No area.** A changed path in no area: `review.route.default`, else `owner-review`.
6. **Paths.** Each `review.route.paths` entry whose glob matches a path of 4.2 (old and new paths alike): its route. An entry at `auto-merge-eligible` keeps it only while the diff size is at most its `maxDiffLines` and the uncovered share at most its `maxUncoveredShare`; past either, it gives `owner-review`. The floor reads the configured route and `maxDiffLines` only.
7. **Score.** With `--score <s>`: `senior-review` when `s >= seniorScore`, `owner-review` when `s >= ownerScore`. A `--score` with neither threshold configured is a setup error (exit 2, `route: --score needs review.route.ownerScore or seniorScore`).

A change with no changed path and no changed rule source takes `review.route.default`, else `owner-review`.

### 6.3 The command

`houserules route --base <ref> [--head <ref>] [--audit <file> | --no-audit] [--score <s>] [--json <file>] [--dir <dir>]` prints `route: <route>` (with `--no-audit`: `floor: <route>`), then the reason lines at that route, sorted, one per reason; a rule that names paths prints at most 20 of them and then `and <k> more`:

- `rule sources: <path> changed -> senior-review`
- `failed: <id> -> owner-review`
- `warned: <id> -> <route>`
- ``area `<name>`: <route>`` (the configured route; the name prints as a code span, 4.8)
- ``area `<name>`: diff <n> lines > maxDiffLines <m> -> owner-review``
- ``area `<name>`: uncovered share <s> > maxUncoveredShare <m> -> owner-review``
- `no area: <path> -> <route>`
- `path <glob>: <path> -> <route>`
- `path <glob>: diff <n> lines > maxDiffLines <m> -> owner-review`
- `path <glob>: uncovered share <s> > maxUncoveredShare <m> -> owner-review`
- `score <s> >= seniorScore <t> -> senior-review`, `score <s> >= ownerScore <t> -> owner-review`
- `default -> <route>` (no changed path and no changed rule source)

A share prints with two decimals; in a limit line, the share rounds up and the limit rounds down, so the printed share is greater than the printed limit. A path prints as 4.8 says. It exits 0 for every route; exit 2 for the setup errors of 4 and 6.2, and for a `--score` outside 0 to 1, with `route: --score <s> is outside 0 to 1`.

### 6.4 The decision document

`houserules/route@1.0.0`: `schema`, `install`, `head`, `route`, `floor` (`true` for a `--no-audit` document), `inputs` (`failed`, `warned`, `areas` with their changed paths, `no_area` paths, `paths`, `diff_lines`, `uncovered_share` or `null` in a floor, `score`, `rule_sources_changed`), and `reasons`: one object for every rule of 6.2 that was evaluated, with `rule`, `input`, `value`, `threshold` (or `null`), `route`, `paths` (at most 20) and `more_paths` (a count), and `decisive` (`true` for a reason at the final route). Every input appears whether or not it raised the route (issue 66). The document holds no sample (8.5).

## 7. The evidence bundle (HR-179; design.md 231, 239, 245)

### 7.1 The section

The bundle is a section of the pull or merge request description:

````markdown
## Evidence bundle

Purpose: <one or two sentences>
Intent: file:docs/plans/2026-10-24-rate-limit.md
Work items: HR-179, HR-185
Risk tier: standard
Criterion: <the criterion that selected the tier>
Budget reason: <only when the diff is above the tier's budget>

```houserules-run
{"schema":"houserules/capture@1.0.0","argv":["mise","run","test"],...}
<the last lines of the run's output>
```
````

The section runs from its heading line to the next line that starts with `## ` outside a fenced block, or to the end of the description; a line inside a fenced block never starts or ends a section. A fenced block opens at a line that starts with three or more backticks and holds no other backtick, and closes at the next line that starts with at least as many backticks followed only by spaces; `bundle check` and the CI units' `Intent:` reader read fences by this one rule. `Intent:` is optional; when it names an intent whose adapter gives a `why`, `Purpose:` may be left out, and the why is the purpose. Each run is a fenced block with the info string `houserules-run`. Its first line is the header line of a capture file, byte for byte; the lines after it are the tail of the capture's output (issue 58, point 1), which no check reads. A fence is one backtick longer than the longest backtick run inside the block.

### 7.2 `bundle write`

`houserules bundle write [--purpose <text>] [--intent <source>:<ref>] --work-item <id>... --tier <name> --criterion <text> [--budget-reason <text>] --capture <file>... [--tail <n>] [--out <file>]` writes the section to stdout or `--out`. It copies each capture's header line and the last `--tail` lines of its output (default 20) from the file, so no header passes through a model (5.137, O7). It exits 2 for a capture that does not parse (the line of `capture`'s reader), neither `--purpose` nor an `--intent` whose adapter gives a why, an empty tier or criterion, no `--work-item`, no `--capture`, and an unwritable `--out`.

### 7.3 `bundle check`

`houserules bundle check --body <file> --base <ref> --head <ref> [--author <login>] [--head-ref <branch>] [--dir <dir>]` reads the request description from a file and runs no audit. With `--author` in `review.bundle.exemptAuthors`, or `--head-ref` matching a glob of `review.bundle.exemptBranches`, it prints `bundle check: <login or branch> is exempt` and exits 0. Otherwise it prints one line for each finding and exits 1 when one exists. Every line that the command prints, on stdout and on stderr, starts with `bundle check: ` (clap's usage errors and the install guard that every command shares come before it runs and print no description text), so no description text starts a line of the job log (a GitHub line that starts with `::` is a workflow command), and every description value prints as 4.8 says:

- `bundle check: no "## Evidence bundle" section` / `bundle check: <n> "## Evidence bundle" sections; keep one`;
- `bundle check: no <Purpose|Work items|Risk tier|Criterion> line` (missing or empty; `Purpose` not when an `Intent:` gives a why);
- `bundle check: intent <source>:<ref>: <the adapter's line>` (no such adapter, no such intent at the head);
- a work item that the tracker does not resolve: `bundle check: work item <id>: <the adapter's line>`; with no tracker, `bundle check: <n> work items not resolved: no tracker (run houserules init --tracker <name>)` and exit 0 for this part, as `audit`; with a tracker that cannot be reached, `bundle check: <n> work items not resolved: <the tracker's line>` and exit 0 for this part (4.9);
- `bundle check: no houserules-run block`; `bundle check: run <i>: the first line is no capture header`; `bundle check: run <i> (<argv>) ran at <head7>, not at <head7>`; `bundle check: run <i> (<argv>) ran in a dirty work tree`; `bundle check: run <i> (<argv>) exited <n>`;
- with `review.bundle.budgets`: `bundle check: risk tier "<name>" has no budget; review.bundle.budgets names <keys>` and `bundle check: diff <n> lines > <tier> budget <m>; add a Budget reason line`. Without budgets it prints `bundle check: no diff budgets configured (review.bundle.budgets)` and checks no size.

A clean bundle prints `bundle check: ok (<n> runs at <head7>, diff <lines> lines)`. `<argv>` prints shell-quoted, as `capture` records it.

## 8. The change record (HR-192)

### 8.1 Storage

A record is a git note on the commit it is keyed by: the last commit of a push to the default branch (the squash commit of a squash merge, the merge commit of a merge commit, the last rebased commit of a rebase merge, the request's own head of a fast-forward). The record lists every commit of its range, so `record show` finds it from any of them. The notes ref is the install's own: `refs/notes/houserules` for a top-level install, `refs/notes/houserules-sub/<install path>` for a subdirectory install (5.168). `record write` writes the note locally, or the note's bytes to a file with `--out`; only the CI units push the ref (5.116). A reader without the ref gets one line: `no change records here; fetch them: git fetch origin <ref>:<ref>`. Git notes are git data, so a record lives on GitHub and GitLab alike.

### 8.2 The document

`houserules/change-record@1.0.0`: `schema`, `install`, `key`, `base`, `head`, `merge_base`, `commits` (a list, or after 8.4 `{count, first, last}`), `written_by` (`houserules <version>`), `host` (`github`, `gitlab`, or `null` for a local write), `rules` (`merge_base_hash` or `null`, `merge_base_rules` (`present` or `absent`), `head_hash`, `audited_with`: `"head"`, and `packs`, as 5.9 gives them), `audit` (the summary, each row's `id`, `mode`, and `result`, the reference summary, and `error`: `null` or the line of an audit that could not run), `intent` (4.9), `evidence` (the 5.9 document without its own `rules`, `intent`, and `route`), `route` (6.4, computed at merge over the pushed range), `sample` (8.5), `bundle` (the parsed section of 7.1: purpose, intent line, work items, tier, criterion, budget reason, and each run's `argv`, `exit`, `head`, and the SHA-256 of its header line; or `null`), `reviewers` (the approvers, sorted, unique, at most 20 names, each cut to 100 characters, and no more names than keep the serialized `reviewers` array within 3,072 UTF-8 bytes), `reviewers_more` (the count of the names left out, or absent), `reviewers_pending` (`true` when the record holds no reviewers yet: a GitLab `record-push` has not set them, 10.4, or the approvers could not be read and stay unknown, 10.1 and 10.4; `record show` prints `Pending: no later job has set the reviewers, or the approvers could not be read.` under its reviewers heading; amended at the T19 review), `links` (`work_items`), `post_merge_audit` (`null` or `{verdict, by, note}`), and `truncated`. `record write` computes `rules` from git and accepts no value for it, so a record cannot claim another rule package; `record show` recomputes `merge_base_hash` (when `present`) and `head_hash` and fails a mismatch (issue 72's acceptance).

The route in the record is the one computed over the range that landed (C8). A project that wires an external score into the request's route wires the same score into the record job (7.6); the units wire none.

### 8.3 The commands

- `record write --base <ref> --head <ref> [--key <sha>] [--audit <file>] [--bundle <file>] [--intent <source>:<ref>] [--reviewer <login>]... [--reviewers-pending] [--score <s>] [--host github|gitlab] [--out <file>] [--dir <dir>]`: computes the record and writes the note on `--key` (default `--head`) in the install's ref, or its bytes to `--out`. `--reviewers-pending` writes `reviewers: []` and `reviewers_pending: true` and budgets the note 4,096 bytes below `maxBytes`, the room that the edit of 10.4 may fill. `--bundle` is the request description; without `--intent`, the bundle's `Intent:` line names it. A key that already has a record in the local ref is replaced only when its `merge_base_hash` and `head` are equal (a re-run of the same push), and the new record keeps the old `post_merge_audit`; otherwise exit 1, `record: <key7> already holds a record of another range`. The rule holds with `--out` too: it reads the local ref, which the units fetch first. An audit that cannot run (a runner tool that is not installed) or a tracker that cannot be reached does not stop the record: `audit.error` holds the audit's line, or the reference summary its failures; `record write` prints the line on stderr and exits 0, because every pushed commit gets a record.
- `record show <sha> [--json] [--dir <dir>]`: the record of the commit or of the record that lists it: a Markdown summary (the packet's sections, the route, the sample, the reviewers, the post-merge audit), or the document with `--json`. Exit 1 for no record (`record: no record for <sha7>`) and for a hash mismatch (`record: <key7> claims rules <hash12> at <the merge base|the head>; git gives <hash12>`). Exit 2 when the merge base is not in the clone (`record: <mb7> is not in this clone; fetch the full history to check the rules hash`).
- `record list [<range>] [--sampled] [--json] [--dir <dir>]`: one line per record, by the committer date of its key, newest first, ties by sha: `<key7> <route> <n> reviewers <sampled|-> <pass|fail|unaudited>`. `--sampled` keeps the sampled records. In a shallow clone, a range reaches past the history of the clone when the commits of either side that the other side does not reach (the symmetric difference of its two ends; for a range of one revision, the commits it reaches) include a shallow commit, when an end is a full object name that the clone lacks, or when an end is a relative revision (`<rev>~<n>`, `<rev>^<n>`) that does not resolve while its base `<rev>` does. Such a range is exit 2 with `record: <range> reaches past the history of this clone; fetch the full history to read its records` (the range reader's line; `stats` has no prefix of its own). Any other end that git cannot resolve, an abbreviated object name included, stays `bad range "<range>"`, because it cannot be told from a typo (amended at the T10 review and its fix-diff review).
- `record audit <sha> --verdict pass|fail --by <name> [--note <text>] [--dir <dir>]`: sets `post_merge_audit` in the local ref; every other byte of the record stays. `--by` is cut to 100 bytes and `--note` to 1,000 bytes of UTF-8, each on a character boundary. A second audit of the same record is exit 1, and so is an audit that would bring the record past `maxBytes` (`record: the audit would bring <key7> to <n> bytes > maxBytes <m>`). The project pushes the ref.
- `stats --records <range>`: adds `review_coverage` to the stats output: the records in the range, those with at least one reviewer, both counts per route and per area, the sampled count, and the audited count with its verdicts. Without workspaces, stats prints only that key. Its range follows the shallow-clone rule of `record list`.

### 8.4 The size budget

`review.record.maxBytes` (default 65,536 bytes of the serialized note; at least 8,192). Over the budget, `record write` shortens, in this order, each step only while still over, and names each step's field in `truncated`: (1) each uncovered path's `ranges` to its line count; (2) the `evidence` text of each passing and judged row; (3) the evidence path lists to a count per kind; (4) `commits` to `{count, first, last}`; (5) the route inputs' path lists to counts, and each reason's `paths` to its first 20; (6) the audit rows to the summary; (7) the bundle's purpose, criterion, and budget reason, and each intent's why, to 1,000 characters, the intent's `artifacts` to a count, its work items, `links.work_items`, and the evidence's `work_items` to the first 50 and a count (`work_items_more` for the evidence), its runs to the first 20 and a count; (8) the minimal record: `schema`, `install`, `key`, `base`, `head`, `merge_base`, `written_by`, `host`, `rules` without `packs` (the head hash names the rules), the audit summary, each intent's `source` and `ref` (at most 10, each `ref` cut to 150 bytes of its serialized JSON form), `route` with `route` and `floor` only, `sample`, `reviewers`, `reviewers_more`, and `reviewers_pending` (capped as 8.2 says), `post_merge_audit` (its `by` cut to 100 and its note to 1,000 bytes of serialized JSON), and `truncated: ["all"]`. Every cap of step 8 counts the serialized UTF-8 bytes of a string without its quotes, an escaped control character included, and cuts on a character boundary. The minimal record holds no list beyond these fixed caps and takes at most `maxBytes` less 4,096 bytes at every cap, so the 4,096-byte reserve of `--reviewers-pending` holds the reviewers of 10.4 (at most 3,072 bytes) and a record stays within `maxBytes`: every push gets a record.

### 8.5 The sample

When a record's route is `auto-merge-eligible`, `record write` draws the sample on the record's key: the record is sampled when the first eight bytes of SHA-256 of `houserules-sample:<key sha>`, read as a big-endian integer and divided by 2^64, are below `sampleRate`. A re-run on the same key gives the same answer. Under a host merge that writes a new commit, the author cannot know the key, and so the draw, before the merge; under a fast-forward merge the key is the author's own head, and the draw is known before the merge (design.md 241). `sample` is `null` for any other route.

## 9. Published schemas (HR-187, 2.0.0 part)

1. Each document carries `"schema": "houserules/<name>@<semver>"` as its first key: `rule-package` (`for` and `for --full`), `audit-result` (`audit`'s stdout and `--json`), `capture` (unchanged), `evidence`, `route`, and `change-record`. Each starts at `1.0.0`. The read schemas keep their own ids. `get`, `index`, `standing`, `topics`, `list`, and `stats` emit no published document (C4).
2. **Typed output (design.md 237).** Each published document is serialized from a Rust type that derives `Serialize` and `schemars::JsonSchema`. `audit` (with the rows that `rules/runner/*.rs` builds and `runner/report_field.rs` compares) and `for` move from a `serde_json::Value` builder to these types. The audit result type is its own type, apart from the deliverables types, because its judged rows hold `open`; the module doc of `rules/audit.rs` says so. A full entry of `for --full` stays a `serde_json::Value` inside the typed package, because the topic files order keys differently (2); its schema is an object that requires `id`, `kind`, `area`, and `summary`, describes `standing` as a boolean, and allows every other key, so one `rule-package` schema describes both forms: an index row always holds `standing`, and a stored entry need not (65 of 133 entries of this repository hold none; the T1 review, `task-1-review.json` issue 2). The proof of byte identity is a diff of the existing goldens (`tests/goldens/read-parity/`, `tests/goldens/audit/`, and the `runner_pins` pins) in which each changed file gains only the `schema` line.
3. **Generation.** A dev binary `gen-schemas` writes each schema to `schemas/<name>/<semver>.json`, with `SchemaSettings::draft2020_12()` and `for_serialize()`, the `schemars` features `preserve_order` and `indexmap2`, `$id` set to the Pages URL of the file, and the `schema` key described as a `const` of the document's own id. `gen-schemas --check` fails when a committed file differs from the generated one; CI runs the check.
4. **Immutability.** `schemas/published.json` lists each published file with its SHA-256. A test fails a listed file whose bytes differ or that is missing, and a file under `schemas/` that the manifest does not list.
5. **The entry (design.md 236).** `houserules.published-documents-carry-their-schema` (area `cli`, not standing): each published document carries its schema id and version; an added optional field is a minor version; a removed or renamed field, a new required field, or a narrower type is a major version; a change of the schema text that changes no document (a generator update) is a patch version; the CLI's major version rises only when a schema it emits by default takes a major version (5.117, 5.146(1)); the read schemas, commands, and flags follow D2 (5.146(2)).
6. **Pages (design.md 232).** `.github/workflows/schemas.yml` (this repository only) deploys a site whose root holds the directory `schemas/` (so a file keeps its `schemas/` segment) to GitHub Pages on a push to `main` that changes `schemas/**`, and on `workflow_dispatch`, with `pages: write` and `id-token: write`. A file is at `https://jblossey.github.io/houserules/schemas/<name>/<semver>.json`. Enabling Pages with the source "GitHub Actions" is a repository setting: the owner does it, or allows the controller to do it, before the merge (18).

## 10. CI wiring (HR-245; design.md 244, 245, 246)

### 10.1 The jobs and their trust

Every way of wiring runs the same five jobs. On GitHub they are the jobs of one workflow; on GitLab each job name carries the install's key (`houserules-<key>-gates`, where `<key>` is `root` for a top-level install and otherwise the install path with each character outside `A-Za-z0-9_-` replaced by `-`, design.md 258; the `key` input of 10.2 holds it), so two installs of one repository never share a job. `ci print` and `ci write` refuse an install whose key equals the key of another install of the repository, with `ci: <path> and <path> share the key <key>; rename one install folder`.

- `gates` (read-only): installs houserules (10.6), runs the `setup` command (10.2) when given, then `check-knowledge`, `check-backlog`, and, on a request, `audit --json` once, the description into a file (10.4, 10.5; never through a command line or a `${{ }}` expression), `bundle check`, `evidence --audit`, and `route --audit`, uploaded as the artifact `houserules-evidence-<key>`. The evidence and route steps run even when an earlier step failed; when the audit step wrote no result, they run the audit in process. The request's head is the source head (10.4, 10.5), never a temporary merge commit.
- `floor` (read-only, requests; design.md 242): installs houserules from the `floor-install` input (10.6), never from `setup`, runs no project tool, and runs `route --no-audit`. Its route reaches `report` bound to the job: on GitHub as the job output `route` (`needs.floor.outputs.route`), on GitLab as the dotenv report of the floor job, which `report` reads through `needs: [{job: houserules-<key>-floor, artifacts: true}]`; a document that another job uploads under a floor name is never read (C18).
- `report` (requests; after `gates` and `floor`, also when they failed): runs no houserules and checks out no project code. It reads the `route` value of each document and accepts only the three values. The applied route is the higher of the two; a missing or invalid floor document means a floor of `owner-review`, so the applied route is at least `owner-review` then (design.md 246(3)), and a missing or invalid gates document leaves the floor alone; each case prints one notice. Before it writes, it reads the request's current head (GitHub: `gh api repos/<repo>/pulls/<n> --jq .head.sha`; GitLab: the request's `sha` from the read of 10.4) and writes nothing when that differs from its own head, with one notice, so an older run never overwrites a newer one. It inserts the applied-route line of 5.2 into the packet, posts or updates the one comment of the install (the newest by the poster's own account whose first line is the marker of 5.2), sets the commit status `houserules/route` (or `houserules/route (<install>)`) on the source head (state success, description the applied route), creates the three labels when missing, and sets `houserules: <route>` (or `houserules <install>: <route>`), removing the install's other two. A refused write (a read-only token) prints one notice and exits 0. On GitHub, `concurrency` with `cancel-in-progress` per request and install also cancels an older `report`; on GitLab, the head check alone keeps the newest head's route, because auto-cancel and `resource_group` neither cancel a started job nor order runs (`spec-review-r3.json`, T13).
- `record` (read-only; a push to the default branch, on GitLab only when `CI_PIPELINE_SOURCE` is `push`, so a scheduled or manual pipeline writes no record): fetches the install's notes ref, installs houserules, runs `setup`, `audit --json`, finds the merged request of the commit, writes its description to a file, and runs `record write --out` (on GitHub with `--reviewer` for each approver, or with `--reviewers-pending` and the notice `houserules: the pull requests of <key7> cannot be read, so the record keeps reviewers_pending` when the read of the commit's pull requests, of the merged request, or of its reviews fails, because the approvers are then unknown (amended at the T18 review); on GitLab with `--reviewers-pending` but for a push whose listing holds no merged request, 10.4); it uploads the note. A push whose `before` is all zeros uses git's empty tree as the base (4.1); `audit` takes no empty-tree base, so that job runs no `audit --json` and `record write` audits the range in process (4). A push whose `before` commit is not in the clone (a force push) writes no record: the job prints `houserules: <before7> is not in this clone (a force push?); no record for this push` and exits 0 (design.md 259); the `record-push` job then pushes nothing and exits 0. A push with no merged request writes a record with no bundle and no reviewers. A `record` job that cannot read the install's notes ref on the remote (`git ls-remote` fails) exits 1 with `houserules: cannot read the notes ref <ref> from the remote` and writes no record; a re-run of the job writes it (amended at the batch-37 branch review). It holds the tracker access of its form (10.7).
- `record-push` (write, after `record`): runs no houserules and no project tool. It fetches the key commit and the notes ref, adds the note on the key with `git notes add -F` only when the fetched ref holds no note there (a re-run never removes a `post_merge_audit`; it prints one notice and keeps the remote note), and pushes with up to three tries of fetch into a side ref, `git notes merge -s theirs`, and push. A third rejection fails the job with one line.

The invariant: no job that runs houserules, `setup`, or project code can read a write credential. On GitHub each job's `permissions` (10.2) gives the write scopes to `report` and `record-push` only; on GitLab only those two jobs name the environment that holds the token (10.4). The route that `gates` computes runs beside the project's tools, so a tool could change it; the `floor` job runs none and takes its binary from a source that the request did not change, and the applied route is at least its floor, so no tool lowers the route below the rule-source, area, path, no-area, and diff-size floors (design.md 242). The record's route is computed beside the project's tools (C11). A fork's request runs the read-only jobs only; its packet goes to the GitHub step summary, or to the GitLab job log and the artifact, and nothing is posted (design.md 233). Both hosts run the CI definition of the request itself, so a request that edits a file of `review.ci.files` controls the status, the label, and the floor of its own run: a required status binds nothing there (GitHub Actions sets it for the edited workflow too), and the floor is computed by the edited jobs. The mitigation that binds is a required code-owner review of the files of `review.ci.files` (a `CODEOWNERS` rule with "require review from code owners" on GitHub; code owners with approval rules on GitLab, a Premium feature); 7.6 says so.

No write job prints a credential: the units set no shell trace (`set -x`), unset `GIT_TRACE`, `GIT_CURL_VERBOSE`, and `GIT_TRACE_CURL` in the write jobs, and on GitHub register the base64 form of the credential with `::add-mask::` before its first use.

### 10.2 The published units (design.md 245)

This repository publishes two units with each release, which the binary embeds with `include_bytes!`, outside `template/` and the kit payload (design.md 251, 253): the GitHub unit's one source is `.github/workflows/houserules-review.yml`, and the GitLab unit's is `ci/gitlab-review.yml` at the repository root. The GitLab unit holds its release version once, in a line that release-please bumps through `extra-files` (`release-please-config.json`), and a test pins that line to the crate's version, so the published file, the embedded file, and the integrity hash that `ci print` prints are the same bytes at each release (C16). The GitHub unit holds no release version, because release-please's token cannot change a workflow file and Dependabot updates the file's action pins (design.md 253): it takes the release to install from its `version` input, and it holds a minimum version, which a person raises by hand in the change that makes the unit call a newer command.

- **GitHub:** `.github/workflows/houserules-review.yml`, an `on: workflow_call` reusable workflow. Its inputs: `version` (the release whose binary `install: release` and `floor-install: release` install, default empty; a job that installs `release` with no `version` fails with one line, `houserules: the version input is required when install or floor-install is release`; `ci print` and `ci write` fill it with the binary's version, beside the `@<release commit sha> # v<version>` line; the third plan review, `plan-review-r2.json` P42), `dir` (the install path, default `.`), `key` (10.1), `setup` (a shell command run before the audit in `gates` and `record`, default empty), `install` (`release`, default, or `none` when `setup` puts houserules on the PATH), `floor-install` (`release`, default; `runner:<path>`, 10.6; or `default-branch`, which builds houserules from the default branch's commit with cargo and holds only for a repository whose default branch builds houserules, this one), and `tracker` (10.7). Each job's `permissions`: `gates` `contents: read` and `issues: read`; `floor` `contents: read`; `report` `pull-requests: write`, `statuses: write`, and `issues: write` (labels); `record` `contents: read`, `pull-requests: read`, and `issues: read`; `record-push` `contents: write`. GitHub allows no expression in a job's `permissions`, so `issues: read`, which the GitHub tracker needs (10.7), is static on `gates` and `record` for every tracker form: a read of issues beside the read of the code (the plan review, `plan-review.json` P13). The caller grants their union in one job, `jblossey/houserules/.github/workflows/houserules-review.yml@<release commit sha> # v<version>`, triggered on `pull_request` (with `edited`) and on `push` to the default branch.
- **GitLab:** `ci/gitlab-review.yml`, a file with `spec:inputs` (`dir`, `key`, `setup`, `install`, `floor-install` (as on GitHub), `tracker`, `stage` (default `test`), `image` (a pinned image with `git`, `curl`, and `jq`), and `token-environment` (default `houserules-<key>`)), referenced as `include: - remote: https://raw.githubusercontent.com/jblossey/houserules/v<version>/ci/gitlab-review.yml` with `integrity: sha256-<base64 of the SHA-256>` (GitLab 17.9) and `inputs:`. Its jobs run on merge request pipelines and on push pipelines of the default branch.

`houserules ci print --host <host> --mode reference` prints the exact lines for the binary's version, with the `integrity` value of the embedded GitLab file and, for GitHub, the tag and the command that resolves its commit sha (`git ls-remote https://github.com/jblossey/houserules refs/tags/v<version>`).

### 10.3 `houserules ci`

- `houserules ci print --host github|gitlab [--mode reference|inline] [--template] [--dir <dir>]` prints, and writes nothing: `reference` (default) the lines of 10.2; `inline` the full jobs of the host's unit with the inputs filled for this install, for a project that adds them to its own pipeline file; `--template` the request section of 7.4. Unless `--template` is given, it ends with one line on stderr, after the lines on stdout, so that `ci print > <file>` writes a valid file: `ci print: add the file that holds these lines to review.ci.files in .houserules.json, so that a change to it routes to senior-review`. The GitHub forms of `ci print` and `ci write` trigger on a push to the default branch by name: the marker's `defaultBranch`, else the branch that `origin/HEAD` names, else `main` or `master` when `origin/<name>` or a local `<name>` exists, in the order of `durable-sha`; when none resolves, the command exits 2 with `ci: cannot resolve the default branch; set "defaultBranch" in .houserules.json`.
- `houserules ci write --host github|gitlab [--mode reference|inline] [--sha <release commit sha>] [--template] [--out <path>] [--force] [--dir <dir>]` creates a new file of its own. With `--host github --mode reference`, `--sha` is required (design.md 247(2)), and its absence is exit 2: `ci write: --sha is required to pin the reusable workflow; resolve it with git ls-remote https://github.com/jblossey/houserules refs/tags/v<version>`. The file goes by default to `.github/workflows/houserules-review.yml` (GitHub, a caller of the reference or the inline jobs) or `.gitlab/houserules-review.gitlab-ci.yml` (GitLab), with two lines printed: the include line that the adopter adds to `.gitlab-ci.yml` themselves, and `ci write: add .gitlab-ci.yml, which holds the include, to review.ci.files in .houserules.json, so that a change to it routes to senior-review`. The file's first two lines are `# Written by houserules ci write; rewrite it with houserules ci write --force and the flags that wrote it.` and `# houserules <version>` (amended at the T17 fix-diff review: a GitHub reference file needs the `--sha` of the new release, so a bare `--force` exits 2). It never writes into an existing file: an existing path is exit 1, `ci write: <path> exists; houserules writes only a file of its own (use --out for another path)`, unless the file's first line is that comment and `--force` is given. It adds the path to `review.ci.files` (4.1). `--template` writes only the template of 7.4, and prints one line on what the host shows first: `ci write: a GitLab project setting or a group template, or a GitHub organization template, takes priority over <path>` when the host is GitLab, or when GitHub and the repository has no template of its own.
- `--host` defaults to the host of the origin URL when it is `github.com` or `gitlab.com`. With another origin (a self-hosted GitHub, a self-managed GitLab) or none, `--host` is required, and its absence is exit 2: `ci: the origin <host> is no known host; pass --host github or --host gitlab`, or `ci: no origin remote; pass --host github or --host gitlab`.
- `update` reads the second line of each file whose first line is `ci write`'s comment: when its version differs from the binary's, it prints `update: <path> pins houserules <old>; this binary is <new>: run houserules ci write --force with the flags that wrote it (a GitHub reference file takes the --sha of v<new>)`, and writes nothing.

### 10.4 GitLab specifics

- The request is read from `GET $CI_API_V4_URL/projects/$CI_MERGE_REQUEST_PROJECT_ID/merge_requests/$CI_MERGE_REQUEST_IID` with the job token (a read the job token may make, 2), not from `CI_MERGE_REQUEST_DESCRIPTION`, which keeps only 2,700 characters, and not from `CI_PROJECT_ID`, which is the fork's in a fork's pipeline; the author is that response's `author.username`.
- The base of a request is `CI_MERGE_REQUEST_DIFF_BASE_SHA`; the head is `CI_MERGE_REQUEST_SOURCE_BRANCH_SHA` when it is set (a merged results or merge train pipeline, where `CI_COMMIT_SHA` is a temporary merge commit) and `CI_COMMIT_SHA` otherwise; the record's `before` is `CI_COMMIT_BEFORE_SHA` of the default branch's push pipeline.
- A description edit starts no pipeline (2); the bundle check of an edited description runs when the adopter runs the pipeline again or retries the gates job. Section 1 and the skill say so.
- The token: the job token cannot post, set a status, set a label, read approvals, or push by default (2), so `report` and `record-push` read the CI/CD variable `HOUSERULES_TOKEN`, which the adopter creates masked and hidden, with the environment scope `houserules-<key>` (the `token-environment` input). Only `report` and `record-push` name that environment (`environment: {name: houserules-<key>, action: access}`), so `gates`, `floor`, and `record`, which run houserules, `setup`, or the request's code, cannot read it. The preferred token is a project access token (the `api` and `write_repository` scopes, the Developer role); on gitlab.com Free, where project access tokens need Premium or Ultimate, it may be a personal access token of a dedicated member with the Developer role, which reaches every project that member can reach (design.md 246(1)). A token expires after at most 365 days. Without the token, `report` prints the packet to the job log, one notice, and exits 0, and `record-push` prints one notice and pushes nothing. `report` posts nothing when `CI_MERGE_REQUEST_SOURCE_PROJECT_ID` differs from `CI_MERGE_REQUEST_PROJECT_ID` (a fork's request that a parent member runs in the parent project). `HOUSERULES_TOKEN` is not a protected variable, because a protected variable reaches only the pipelines of protected branches and so never a merge request's `report`. The limit that remains: a branch that edits the CI definition can name the environment in a job of its own and read the token; the mitigation is the code-owner review of 10.1, which 7.6 states.
- `record` lists the commit's merge requests with the job token (2) and writes the note with `--reviewers-pending`, but for a push whose listing succeeds and holds no merged request: that push has no approvers, so its note is written without the flag (`reviewers: []`, `reviewers_pending: false`), and `record-push` reads no approvals for it; a listing that fails keeps the flag, because the approvals are unknown (amended at the live run). `record-push`, which holds the token and runs no houserules, reads the request's approvals and sets, with `jq`, `reviewers` to the approvers' usernames (sorted, unique, the first 20, each cut to 100 characters, and no more names than keep the serialized array within 3,072 bytes by jq's `utf8bytelength`; GitLab usernames may hold emoji), `reviewers_more` to the count of the names left out when any, and `reviewers_pending` to `false`; the reserve of `--reviewers-pending` keeps the result within `maxBytes`, in a full and in a minimal record alike, and the result validates against `change-record@1.0.0` (21.5).
- Git over HTTPS takes the token per command (`git -c http.extraHeader="Authorization: Basic <base64 of oauth2:$HOUSERULES_TOKEN>"`), never in a remote URL or the job log.
- Every URL comes from `CI_SERVER_URL` and `CI_API_V4_URL`, so a self-managed GitLab works; one that cannot reach `raw.githubusercontent.com` or the release downloads uses `ci write --mode inline` and `install: none` with its own copy of the binary, and `floor-install` names a binary that the runner image provides (10.6).

### 10.5 GitHub specifics and a self-hosted GitHub

- The description is `.pull_request.body` of `$GITHUB_EVENT_PATH`, written with `jq` (C6); the author is `.pull_request.user.login`, the branch `.pull_request.head.ref`, and the head `.pull_request.head.sha`, which the jobs check out.
- Git takes the job token per command, with the run's own server: `git -c "http.${GITHUB_SERVER_URL}/.extraheader=AUTHORIZATION: basic <base64 of x-access-token:$GITHUB_TOKEN>"`, its base64 value masked first (10.1).
- A self-hosted GitHub (GitHub Enterprise Server) uses `ci write --host github --mode inline` (it cannot call a workflow on github.com by default) and, without internet access, `install: none` with its own copy of the binary and a `floor-install` that names a binary the runner provides (10.6).

### 10.6 Installing houserules in a job

`install` and `floor-install` take `release` (the unit's own release on GitLab, the `version` input's release on GitHub, from this repository's releases, verified as the seeded workflow does today; on GitHub a binary that `release` installed and that is older than the unit's minimum version fails the job with one line, `houserules <v> is older than <min>, which this unit needs; raise the version input`; the check runs only for `release`, because `none`, `default-branch`, and `runner:<path>` bring a binary that names no release; the minimum at batch 37 is `2.0.0`, the first release with the commands of this spec), and `install` also `none` (`setup` puts houserules on the PATH). `floor-install` also takes `default-branch` (build houserules from the default branch's commit, never the request's; only in a repository whose default branch builds houserules) and `runner:<path>` (a binary that the runner image provides at `<path>`; design.md 247(1)), which holds only where the runner is fresh per job (a GitHub-hosted runner, a GitLab docker executor) or the runner user cannot write `<path>`, because on a reused runner the request's `gates` job could replace the file (C19); it never takes `none`, because the floor must not run a binary that the request built (design.md 242, 246(3)). The seeded `knowledge.yml` of an existing install keeps installing the stamped version (10.7).

### 10.7 `init`, `update`, and an existing seeded workflow (design.md 245)

- `init` writes no new CI file and, when the install holds no seeded workflow after the run, prints: `init: houserules wrote no CI file; to run the gates and the review layer in your pipeline, run houserules ci print --host <host>`, where `<host>` is the detected host (10.3), or the literal text `github or gitlab` when no host is detected. The `origin_is_github_hosted` seeding of `install/mod.rs` goes, and `update` no longer writes the workflow again when it is absent.
- An existing install that holds the seeded `.github/workflows/knowledge.yml` (or `knowledge-<folder>.yml`) keeps it: it stays a D3 file, and `update` keeps maintaining it for the gates through its baseline, as today, with the read-only token of design.md 226; it adds no review job to it. Once per install, recorded as `reviewLayerOffered: true` in `.houserules.json` (an install-schema addition of `2.3.0`), `update` prints: `update: <path> runs the houserules gates; to add the review layer, run houserules ci print --host github`. An install whose seeded workflow is absent gets no workflow and no line.
- An adopter-modified seeded copy is kept, and `update` prints its gates hand steps as in batch 36, every marker read per job: the gates job is each job with a step whose `run` holds `houserules check-knowledge`, read with `saphyr` (design.md 238) whatever its key and indentation; its `permissions` decides the step as design.md 226 says, and a mapping with `contents: write` gets `<path> grants contents: write in the <job> job; replace it with contents: read` (HR-243); a mapping that holds a needed scope with any other value than `read` (for example `contents: none` or `issues: write`) gets `<path> sets <scope>: <value> in the <job> job; replace it with <scope>: read`, never a step that adds a second key. A workflow with no such job gets `<path> has no job that runs houserules check-knowledge; houserules update checks no permissions there`; two such jobs are each checked; a file that does not parse gets `<path> is not valid YAML (<the parser's line>); houserules update checks no permissions there`. houserules writes no YAML into it.
- The `tracker` input gives the units' `gates` and `record` jobs the tracker access of the install, as the seeded forms do (`issues: read` and `GH_TOKEN` for the GitHub tracker; the Beads bootstrap with its persisted read-only credential); `ci print` fills it.

Read: the seeded `knowledge.yml` installs the version stamped in `.houserules.json` (`template/.github/workflows/knowledge.yml`, its install step). Rejected option, installing the version stamped in `.houserules.json`, as the seeded `knowledge.yml` does: best case, the binary always matches the install, and the unit holds no version; a unit that calls a command newer than the stamp then fails. Reversal condition: adopters who pin the unit and the stamp apart and report mismatches; `update`'s pin line of 10.3 narrows that gap.
- C17. The floor's binary never comes from `setup` (10.6). Read: `setup` runs in the request's own code, so a floor built by it is no floor (design.md 242). Rejected option, the floor from `setup` when `install: none`: best case, one install path; the request then chooses its own floor. Reversal condition: none.
- C18. The floor's route reaches `report` as a job output or a job's own artifact (10.1). Read: an artifact name is per run, and `upload-artifact` with `overwrite: true` replaces a same-name artifact, so a name binds no job (`spec-review-r3.json`, T6). Rejected option, an artifact read by name: best case, one mechanism for both documents; the `gates` job, which runs project tools, could stand in for the floor. Reversal condition: none.
- C19. `floor-install: runner:<path>` holds only on a fresh runner or an unwritable path (10.6; design.md 247(1)). Read: a persistent runner or a GitLab shell executor runs the request's `gates` job as the same user as the floor job. Rejected option, `runner:<path>` everywhere: best case, offline installs on any runner get a floor; on a reused runner the request could replace the floor's binary. Reversal condition: a runner that verifies the binary's hash before the floor runs it.
