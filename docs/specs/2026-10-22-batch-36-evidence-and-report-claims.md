## 3. `capture` (HR-171, HR-197)

`houserules capture --out <file> [--force] -- <command> [<arg>...]`

- It runs the command with the arguments as given, with no shell, in the current directory, with the environment of `capture`, and with stdin closed (a command that reads stdin gets end of file, so no capture waits on a terminal). A command that needs a variable or a pipe runs through `env` or `sh -c` (7). One pipe takes both stdout and stderr, so the file holds both streams in the order the command wrote them.
- Before the command starts, `capture` tests its setup in this order and stops at the first error (below): the arguments are UTF-8, the current directory and `<file>` are UTF-8 paths, the directory of `<file>` exists, and `<file>` does not exist (unless `--force`). Then it reads HEAD and the dirty flag of the git work tree at the current directory, then creates its temporary file, so the temporary file never counts as dirty.
- It writes `<file>` once the command ends: line 1 is the header, one JSON object; the rest is the output.
- The header holds these keys in this order: `schema` (`"houserules/capture@1.0.0"`), `argv` (the command and its arguments, an array of strings), `cwd` (the absolute current directory), `start` and `end` (RFC 3339 UTC timestamps with nine fractional digits, written with `jiff`, D9), `exit` (the exit code, or `null` when a signal ended the command), `signal` (the signal number, or `null`), `head` (the full sha of HEAD, or `null` outside a git work tree or before the first commit), `dirty` (`true` when `git status --porcelain` printed a line, `false` when it printed none, `null` when `head` is `null`; when `git status` fails in a work tree, `head` and `dirty` are both `null`), and `lossy` (the number of byte sequences that were not UTF-8 and that `capture` replaced with U+FFFD).
- A capture is a file whose first line parses as a JSON object with these keys and whose `schema` is `houserules/capture@1.x.y`. A reader names any other file "no capture" with one of these reasons: `it is empty`; `its first line is no JSON object`; `its header lacks <key>`; `its schema is <schema>, not houserules/capture@1`.
- The output is UTF-8: bytes that are valid UTF-8 stay as the command wrote them, CR and LF included; each invalid sequence becomes U+FFFD and counts in `lossy`. The output ends where the command's output ends; `capture` adds no newline.
- `capture` streams the output into a `tempfile::NamedTempFile` in the directory of `<file>` (design.md 213), writes the header and the output into a second one there, and persists it at `<file>` with `persist_noclobber`, or with `persist` under `--force`; `persist_noclobber` guards the race where `<file>` appears while the command runs, and prints the same `exists` line. A run that ends with an error removes its temporary files. The file at `<file>` gets the mode a new file gets (0666 less the umask), also under `--force`. A `capture` that is killed can leave a temporary file (named by `tempfile`, starting with `.tmp`) in that directory, never a partial file at `<file>`.
- It prints one line to stdout when the file is written: `<file>: exit <n>`, or `<file>: ended by signal <n>`. It prints nothing of the command's output.
- Its exit status is the command's exit code as the operating system reports it, or 128 plus the signal number; `capture` ends its process with that code after the file is written, so a Windows code above 255 passes whole.
- Setup errors print one line to stderr, write no file at `<file>`, and exit 2: `capture: <file> exists; pass --force to replace it`; `capture: <dir> does not exist` (the directory of `<file>`); `capture: argument <n> is not UTF-8` (`<n>` counts from 0 at the command); `capture: the current directory is not UTF-8`; `capture: the --out path is not UTF-8`; `capture: could not read the current directory: <the OS error>`; `capture: could not start <argv0>: <the OS error>`; `capture: could not write <file>: <the OS error>`. One error follows the start: `capture: could not wait for <argv0>: <the OS error>`, exit 2, and no file at `<file>`. A missing command after `--` is clap's usage error, exit 2. A command that exits 2 also gives exit 2; the file at `<file>` then exists.
- The header's publication as a JSON Schema at a stable URL (5.117) belongs to HR-187 (batch 37); `capture --help` documents its keys.

## 4. The report form (HR-171, HR-057, HR-158, HR-141, HR-204)

Each change is a critical-task change in both copies of the deliverables schema (`template/.claude/schemas/deliverables.json` and the root copy).

- `run` becomes `{ capture, sha256, command, exit, excerpt? }`, with `additionalProperties: false`. `capture` is the capture's path, absolute or relative to the install root (`text`), resolved by `Path::join` onto the install root as `check-report-claims` resolves a path today; an absolute path lets a parallel implementer, whose worktree holds no copy of the workspace, cite its captures. `sha256` is the SHA-256 of the whole capture file, 64 lowercase hex digits (pattern `^[0-9a-f]{64}$`). `command` is the header's `argv` joined by `shlex::try_join` (design.md 209) (`text`). `exit` is the header's `exit` (integer or `null`). `excerpt` is optional: a string of 1 to 1000 UTF-16 code units, the validator's unit. `output` leaves the schema: a report holds no command output inline. The schema description of `run` states the cap and its reason.
- `self_review` becomes an array of `selfReviewItem`: `{ claim, evidence? }`, `claim` a `prose`, `evidence` a `textList` of paths, each absolute or relative to the install root as `capture` is, with no line suffix.
- `taskReport` gains an optional `citations`: an array of `{ path, line, end?, anchor, sha256? }`; `path` and `anchor` are `text`, `line` and `end` integers of at least 1, `sha256` as in `run`. `anchor` is a byte-exact substring of the cited lines that the claim rests on, written by the author; it holds at least three non-whitespace characters in a row (pattern `\S{3}`), and it occurs exactly once in the file at HEAD, inside the cited lines, so a draft line number that a later commit moved cannot pass the first fill, whatever the anchor (C3). The floor alone refuses only one- and two-character anchors; the uniqueness rule refuses `let` and `});`. The hash covers the cited lines of the file at HEAD: from the first byte of line `line` to the last byte of line `end` (or of `line`), without the LF that ends the last cited line. An LF ends a line; a CR before it stays in the line's bytes; a last line with no LF is a line. `report-facts` fills it.
- `fixRound.findings[]` gains an optional `reran`: the path of the review's probe that the round re-ran (`text`, absolute or relative to the install root as `capture` is). It may be absent for a finding whose review gave no reproduction (a naming or a prose finding); the re-review judges an absent `reran` against `process.fix-proofs-extend-the-reviewers-run`.
- Every other kind and part stays as it is.

A run of `tests`, `live_run`, `tdd[].red`, `tdd[].green`, and `fix_rounds[].tests[]` uses this form. `validate` keeps its fix-round invariant on the new field: it reads the output of each `fix_rounds[].tests[]` capture (resolved against the install root; a capture it cannot read is left to `check-report-claims`) and fails an embedded audit result whose `summary.skipped` is above 0 with `<file>.fix_rounds[<i>].tests[<j>].capture: audit summary skipped is <n>; re-run audit with --report`. A report of the old form fails `validate` against the new schema; no gate re-validates a closed report (2), so a closed workspace needs no conversion (12).

## 5. `report-facts` (HR-158, HR-141)

`houserules report-facts <REPORT> --base <ref> [--fix-base <ref>] [--audit <file>] [--dir <DIR>]` (a new subcommand, design.md 214)

The command resolves the install root first, as `check-report-claims` does (outside a repository it prints the `--dir` remedy and exits 2, before it reads `<REPORT>`). `<REPORT>` resolves against the working directory, as `validate`'s arguments do; captures, citations, and git resolve against the install root, as `check-report-claims` does. The command reads the report, fills these fields, and writes the report back with the crate's JSON writer (`emit`, the form every houserules command prints) through a `NamedTempFile` that it persists over `<REPORT>` (design.md 213):

- `commits`: every commit of `<base>..HEAD`, oldest first, each `{ sha: <full sha>, subject }`.
- `files_changed`: the paths that `git diff --name-only --no-renames <base>..HEAD` prints (a renamed file lists both its old and its new path) that lie inside the install root, as install-root paths, sorted (`rules::git_paths`, `InstallPrefix::map`).
- `fix_rounds[<last>].commits`, with `--fix-base`: every commit of `<fix-base>..HEAD`, oldest first.
- `self_audit`, with `--audit`: the file that `audit --json` wrote; its `summary` as written, and the entries of its `rules` array whose `mode` is `deterministic`, in their order, as `rows`.
- Each run that holds `capture`: `command` and `exit` from the capture's header, and `sha256` when the run holds none. A run whose `sha256` differs from the file's is a finding (below): `report-facts` never replaces a recorded hash, so a changed capture cannot pass unseen. To accept a new capture, the author re-reads it and removes the run's `sha256`.
- Each entry of `citations`: the anchor must occur in the cited lines at HEAD and nowhere else in the file; an entry that holds no `sha256` gets the hash of those lines. A recorded hash stays. The command reads a cited file as `git show HEAD:./<path>` run at the install root, so a subdirectory install reads its own file, not a file of the same name at the git top level; "tracked at HEAD" means that the path holds no `..` segment and that this object is a blob (`git cat-file -t` prints `blob`), so a directory or a file outside the install root is "not tracked".

A key it fills that the report lacks is added at the end of the report object. The report's other fields stay as they are, in their order. It prints `<REPORT>: facts filled` and exits 0. Findings print one line each, write nothing, and exit 1: `<label>: capture <path> does not exist`; `<label>: capture <path> could not be read (<the OS error>)`; `<label>: <path> is no capture (<reason>)`; `<label>: capture <path> has sha256 <actual>, but the report records <recorded>; re-read the capture, then remove sha256 and run report-facts`; `citations[<i>]: <path> is not tracked at HEAD`; `citations[<i>]: <path> has <n> lines at HEAD, fewer than <m>` (`<m>` the larger of `line` and `end`); `citations[<i>]: end <end> is before line <line>`; `citations[<i>]: the anchor is not in <path>:<range> at HEAD; re-open the file at HEAD and correct line and end`; `citations[<i>]: the anchor occurs <n> times in <path> at HEAD; choose text that occurs once`. `<range>` is `<line>`, or `<line>-<end>` when `end` is greater than `line`. `<label>` is the run's JSON path (`tdd[2].red`). Setup errors print one line and exit 2: `<REPORT>: <the read or parse error>`; `<REPORT>: kind is not task-report`; `--base <ref>: not a commit` (and the same for `--fix-base`); `--fix-base: the report has no fix_rounds entry`; `--audit <file>: <the read or parse error>`; `--audit <file>: it is no audit result (it needs a summary object and a rules array)`; `report-facts: git log failed: <the error>`; `report-facts: git diff failed: <the error>`; `<REPORT>: could not write: <the OS error>`.

## 6. `check-report-claims` (HR-171, HR-197, HR-141, HR-148, HR-204)

The checks of a report after this batch, in order. Each finding is one line on stderr; exit 1 on any finding. "A capture" is the file of 3.

1. Captures: each run holds a `capture`, which exists, is a capture, and has the run's `sha256`; the run's `command` and `exit` equal the header's. Lines: `<label>: no capture; run the command through houserules capture`; `<label>: no <key>; run houserules report-facts` (one line for each of `sha256`, `command`, and `exit` that a run with a capture lacks, design.md 217); `<label>: capture <path> does not exist`; `<label>: capture <path> could not be read (<the OS error>)`; `<label>: <path> is no capture (<reason>)`; `<label>: capture <path> has sha256 <actual>, but the report records <recorded>; re-read the capture, then remove sha256 and run report-facts`; `<label>: command differs from the capture's (<header command>)`; `<label>: exit <report exit> differs from the capture's <header exit>`.
2. Excerpts (HR-197): each `excerpt` is a byte-exact substring of the output of its run's capture (the bytes after the header line). Line: `<label>.excerpt: not a byte-exact substring of the output of <path>`.
3. The `natural` label (HR-142, HR-204 (6), design.md 211): a `natural` RED whose header `end`, in whole seconds, is later than the committer time of the newest commit the report lists fails with `tdd[<i>]: mode "natural", but the RED capture "<path>" ended <n> s after the newest listed commit <sha> (committed <iso>); label the entry "reconstructed"`; a `natural` RED whose header `exit` is 0 fails with `tdd[<i>]: mode "natural", but the RED capture "<path>" exited 0; capture the failing run, or label the entry "mutation" or "reconstructed"`; a `natural` RED whose header `end` does not parse fails with `tdd[<i>]: mode "natural", but the RED capture "<path>" has an end that is no RFC 3339 time (<the jiff error>)` (design.md 217). The file's modification time is no longer read, so the check also judges a capture that git tracks.
4. Recorded citations (HR-141): each entry's path is tracked at HEAD, `end` is not before `line`, its lines exist there, its `anchor` occurs in them and nowhere else in the file, and its `sha256` (once filled) equals the hash of those lines at HEAD (`git show HEAD:./<path>` run at the install root, as in 5; the blob, so the working tree and its checkout line endings do not matter). Lines: `citations[<i>]: <path> is not tracked at HEAD`; `citations[<i>]: end <end> is before line <line>`; `citations[<i>]: <path> has <n> lines at HEAD, fewer than <m>`; `citations[<i>]: the anchor is not in <path>:<range> at HEAD; re-open the file at HEAD and correct line and end`; `citations[<i>]: the anchor occurs <n> times in <path> at HEAD; choose text that occurs once`; `citations[<i>]: <path>:<range> has sha256 <actual> at HEAD, but the report records <recorded>; re-open the lines at HEAD, correct line and end, then remove sha256 and run report-facts`.
5. Self-review evidence (HR-204 (1), (2)): each `evidence` path exists; an item whose `claim` holds the word every or all, or the phrase no remaining (whole words, any case; the phrases "at all" and "after all" do not count), names at least one capture in `evidence`; an item whose `claim` holds pin, pins, or pinned names at least one existing path. Lines: `self_review[<i>].evidence[<j>]: <path> does not exist`; `self_review[<i>].evidence[<j>]: <path> could not be read (<the OS error>)` (any error but NotFound, design.md 219); `self_review[<i>]: claims "<word>", but its evidence names no capture`; `self_review[<i>]: claims "<word>", but its evidence names no existing path`.
6. Re-run probes (HR-204 (4)): each `reran` path exists and lies in the directory that holds the report or below it. Lines: `fix_rounds[<i>].findings[<j>].reran: <path> does not exist`; `fix_rounds[<i>].findings[<j>].reran: <path> could not be read (<the OS error>)` (any error but NotFound, design.md 219); `fix_rounds[<i>].findings[<j>].reran: <path> is not in the workspace <dir>`.
7. Ephemeral paths (HR-204 (3)): today's rule (a word that starts with `/tmp/`, or a word with a `scratchpad/` segment) applies to every string of the report except `command` (the literal command, where a scratch path is the text that ran), `excerpt` (output data), `citations[].anchor` (text copied from a cited file), the hashes, and `self_audit` (tool output). The line stays as today, with the string's JSON path as its label.
8. The self-audit head, the narrative shas, and the self-audit ratio: kept; the narrative they read is `implemented`, each `self_review[].claim`, and the fix-round `finding` and `fix`.
9. Free-prose line numbers (HR-107, HR-148): kept over the same narrative, and every element of a comma or semicolon list is checked. After `path:<n>` or `path:<n>-<m>`, an element that follows its separator (`,` or `;`) with no space always continues the list, whatever follows it (the word is whitespace-delimited and trimmed as today). An element that follows its separator after one space continues the list only when it ends the text or is followed by a separator, a closing `)` or `]`, or a `.` that ends the sentence (a `.` followed by whitespace or the end of the text); one followed by a word does not. The finding names the whole list token. On a 10-line file, `file.rs:3,999 shows`, `README.md:3,999:`, and `see README.md:3, 999.` fail; `backlog_parity.rs:6, 42 total` reads one citation.
10. Counts beside a cited capture (HR-110): kept for the narrative. It also reads the body of each commit the report lists (`commits[]` and `fix_rounds[].commits[]`) as a field labelled with the commit's JSON path, its sha as listed, and `body` (`commits[<i>] <sha> body`, `fix_rounds[<r>].commits[<i>] <sha> body`; HR-204 (10), design.md 219); there a citation counts only when it resolves to a capture (an absolute path, or a path relative to the install root), and every other citation is skipped, a bare file name that names no capture at the install root included. A cited capture is read without its header line.
11. Sweep coverage (HR-111): kept; a cited capture is read without its header line, as in check 10, so a file named only in the header's `argv` does not count as covered.

Retired by design.md 212, each with the check that covers its subject: the redirected-capture check (check 1: the hash ties the run to its file), the truncation-marker check (check 2: the excerpt is a byte-exact substring), and the paste-run lint (the command comes from the header's `argv`, so no hand-typed command remains). `--doc` and `--item` keep their workspace-path check.
