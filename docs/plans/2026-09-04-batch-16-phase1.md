## Pre-flight notes

- The corpus is dev-only (`tests/corpus/`), never payload. Its
  regeneration test is the JS freeze: any behavior change to the JS
  render/check path breaks `regenerated == frozen` and fails CI.
  This is what lets T3/T4 retire the ported vitest cases while the
  JS files still ship until phases 3/5.
- The template payload does NOT change in this batch: no shipped
  file references the binary until phase 3. Dogfood byte-pins stay
  intact.
- Rust toolchain pins through mise (`mise use rust@…` writes the
  exact version; jdx/mise-action carries it to CI). No second pin
  file unless the windows runner forces rustup — the task records
  the docs-verified decision.
- Windows risk: `tools/kb.sh` is POSIX; only the cargo job runs on
  windows. If mise-on-windows blocks, the fallback is rustup in that
  matrix leg, recorded in the report.
- Crates land only via `cargo add <crate>@=<version>` with
  dependency vetting recorded per task.

## Tasks (strictly sequential)

### Task 1: the frozen fixture corpus (HR-054)

Files: `tools/make-corpus.mjs` (dev-only generator), `tests/corpus/`
(frozen outputs + `manifest.json` with the base sha and input list),
`tests/corpus.test.mjs` (regeneration == frozen; manifest sanity).
Slices: renderAll outputs for this repo's base, byte-exact; a
synthetic minimal fixture base (empty area, budget entry, seeded
check violations) with expected check-knowledge messages and exits;
audit JSON over two recorded historical ranges plus validate
verdicts over archived `.superpowers/sdd/` workspaces; backlog
command outputs (`list`, `get`, `batch`, `check`). Natural RED
first.

### Task 2: cargo workspace, toolchain, CI matrix

Files: `Cargo.toml` (workspace) + the `houserules` binary crate with
`rules`/`backlog`/`install` module boundaries (spec §3), `mise.toml`
(rust pin, cargo test task), `.gitignore` (`target/`),
`.github/workflows/ci.yml` (cargo job: fmt --check, clippy -D
warnings, cargo test on ubuntu/macos/windows). First behavior:
`houserules --version` prints the crate version; smoke cargo test.
Dependency vetting for every crate.

### Task 3: `render` in Rust behind the byte-parity gate

Files: the crate's `rules` module (serde models for the knowledge
surface render needs, the glob union matcher, renderAll, `render`
and `render --check` commands), cargo tests. The matcher is the
first parity target (`houserules.glob-union-matcher`): its vitest
cases port to cargo tests. Gate: corpus byte-parity for every
rendered file on both corpus bases. The ported vitest render cases
leave `tests/kb.test.mjs` in the same commit.

### Task 4: `check-knowledge` in Rust

Files: the `rules` module's check path (shape checks, budgets, the
160-character summary cap, area/glob validation), cargo tests.
Gate: message and exit byte-parity against the corpus ok-and-seeded
slices. The ported vitest check cases leave in the same commit.

### Task 5: the cross-compilation spike (spec phase-4 input)

Research task, docs-verified: cargo-dist against cross/zig for the
release matrix (linux x86_64/arm64, macos x86_64/arm64, windows
x86_64). Deliverable: working release-shaped builds or documented
blockers, and a written comparison in the workspace; the
recommendation goes to the batch report for the owner's phase-4
ruling. No release machinery changes in this batch.
